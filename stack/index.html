Operating the cluster — the runbook canon

  1. I've operated petabyte-scale ClickHouse clusters for 5 years (Part I)
    Tinybird · Javi Santana, 2024, post

    The architecture bible. Don't shard prematurely ("re-sharding was super hard"). ZK on isolated machines. Capacity rule: 32 cores ≈ 5GB/s. Wait a month after any release. Batch inserts, aim for one part per insert.

  2. Lessons learned from 5 years with ClickHouse clusters: Part II
    Tinybird · Javi Santana, 2024, post

    The monitoring + DDL runbook. ON CLUSTER stalls when a replica is down. "Read only tables → you are fucked" recovery: drop, recreate, let replication refill. The POPULATE-is-broken warning and the uniqExactState-kills-merges warning both originate here.

  3. Hunting orphan objects: 45% off our storage bill (and a near data-loss incident)
    Tinybird · Irene Martínez, May 2026, post

    A cleanup job that continued on incomplete snapshots classified live objects as dead → "file not found" at query time. Two paths on disk: runtime uses store/<uuid>/, backups use data/<db>/<table>/. Pre-stage the UUID↔table map before you need it.

  4. How we handle service disruptions
    Tinybird · Jorge Sancha, 2020, post

    28-min outage from config drift — one environment had a different data path. Two lessons: LB health checks must verify data returned, not just liveness; and staging-passes ≠ prod-safe when config has drifted.

  5. Why we maintain a ClickHouse fork at Tinybird
    Tinybird, 2025, post

    Doubles as an upgrade-pain field report. "Pretty much any time you upgrade you have some issues." Documents the UNION + MV silent-drop regression in 25.8.1.477. The case for a query-replay validation harness before every upgrade. Zero-copy disabled by default ≥ v22.8.

  6. We added the Backup Database engine to ClickHouse
    Tinybird, 2025, post

    Backup Database engine ships in 25.2. Attach a backup as a read-only DB in seconds — no full restore. The cheapest way to run production-data upgrade validation without a parallel cluster.

  7. Resolving a year-long ClickHouse lock contention
    Tinybird · Villar / Kita, 2023, post

    CPU at 20% but QPS capped → contention, not resources. They added ContextLockWaitMicroseconds (PR #55029) to make it visible, then refactored Context. Result: 3× QPS at concurrency 500, 5×+ at 1000. Put this profile event on your dashboards day one.

ReplacingMergeTree — dedup at merge, not insert

  1. ReplacingMergeTree engine reference
    ClickHouse Docs, official

    "Eventual correctness only — don't rely on it." Highest version wins; is_deleted only filters under FINAL. OPTIMIZE FINAL CLEANUP needs the experimental flag. Deletes recommended only for <10% delete rate.

  2. Working with ReplacingMergeTree (operator guide)
    ClickHouse Docs, official

    do_not_merge_across_partitions_select_final=1 parallelizes FINAL per partition. The merge-stops-trap: parts past max_bytes_to_merge_at_max_space_in_pool never auto-merge again — schedule OPTIMIZE on cold partitions.

  3. ReplacingMergeTree — The Good, The Bad, The Ugly
    Altinity, 2023, post

    The honest tradeoff write-up. Why clean_deleted_rows='Always' had correctness issues on replicated tables (issue #50346) — prefer scheduled OPTIMIZE FINAL CLEANUP until verified for your version.

  4. SYSTEM RESTORE REPLICA after metadata loss
    Altinity, 2021, post

    Bulk corrections via insert-higher-version (not ALTER UPDATE). When metadata is lost a replica attaches read-only; SYSTEM RESTORE REPLICA … ON CLUSTER rebuilds it without deleting data.
