How to know a backfill is safe to swap before you swap it

4 November 2026

"It ran" and "it produced rows" tell you nothing about whether replacing production with it is safe. That is a separate proof — and the gate that proves it caught a silent regression on the very first sample.

A backfill reprocesses a past window of an event stream into a separate table, and swapping replaces the matching production partitions with the reprocessed ones. Production here is a ClickHouse ReplacingMergeTree, which keeps, per key, the row with the highest version — once the parts have merged.

I had a backfill reading real bronze — the raw captured events — and landing its rows in a local ClickHouse: rows landed, exit code zero. That is where the harder question starts: is this output safe to put into production? A backfill exists to replace or repair what production already has, and it can do that job worse than the live pipeline did while reporting a clean success. So before any swap, I built a reconciliation gate whose only job is to answer that question. Six things it taught me.

1. There are two reconciliations, not one, and they answer different questions

I kept conflating them until I forced them apart.

The first is source against destination: is the source record faithfully transformed into the destination row? You read the source, recompute the expected row with the exact production mappers, and diff field by field. This proves the transform is correct.

The second is backfill against live: does my reprocess output match-or-improve what the production stream has already written, keyed by the business id? This compares two destinations — my reprocess and live production — and it is a no-regression gate before any swap. Its motto is the whole point: do a better job, and do not mess up.

Passing one does not imply the other: a perfectly correct transform can still regress production, and it took a real example for me to see how.

2. The gate earned its place on the first sample

The first real cross-verify I ran — a handful of random ids, my backfill against live production — flagged two of five as regressions immediately. Not transform bugs. Regressions: my output was worse than what production already had.

My backfill read a one-hour window. It caught the open event — status PENDING — but it clipped the completion event, because the completion's event time falls after the window. The live pipeline sees the whole continuous stream, so it had already moved that record to COMPLETED. If I had swapped my output in, I would have overwritten a COMPLETED record with PENDING. A successful-looking backfill, quietly walking production backwards.

The trap is general: any window-bounded reprocess of an event stream clips the late events that complete a record. The thing that opens a record lands inside your window; the thing that completes it lands outside. Your reprocess looks complete and is not. The no-regression gate exists to catch exactly this, and it did so on its first sample — the best argument I have for building the gate before you think you need it.

3. Pad the late events, anchored on the one that defines the window — and size the pad to the tail

The fix is a read-window pad. For the late-arriving completion events, read past the end of the window, so a record opened near the boundary still picks up the event that completes it. Crucially you do not pad the event that anchors the window; that one defines what you are reprocessing, and padding it would pull in records you did not mean to touch.

The pad has to cover the tail of your open-to-complete latency, not the median. Completion events can trail the open event by hours, and sometimes by more than a day — slow downstreams. If you set the pad to six hours and your real ninety-ninth percentile is eighteen, you are still clipping late completions, and your gate will keep flagging them — correctly — as artifacts of too small a pad. So pull the actual open-to-complete latency distribution from a known-good day and set the pad above the tail you care about. A day-level pad is safer, but a two-day-late completion still clips at the day edge. There is no pad that escapes a long-enough tail; there is only a pad that covers the tail you have decided to honour.

4. A good reconciliation tells you the truth about your source, not just your transform

This is the lesson I did not expect.

When the full reconciliation ran, it reported zero open events for the target day. Zero. My first instinct was that something in my pipeline was dropping them. It was not. The source connector that captures those events had been deployed the day after the day I was reprocessing — so the source itself, the bronze, held only completion events for that day and no open events at all. Most of the rows my backfill produced were completion-only placeholders with no matching open event that was ever captured anywhere. Nothing was broken. The source was simply incomplete, and incomplete in a way that no amount of staring at my own code would have revealed.

That is what an honestly built reconciliation buys you: it separates "my transform is wrong" from "my source never had it." The hardest data bugs are upstream-completeness bugs wearing the costume of a pipeline bug, and they cost you time debugging code that is working perfectly. A reconciliation that points at the source instead of at you is worth far more than the fidelity number it prints.

5. Reconcile against the winning row — and do not let coverage pose as fidelity

First, when your destination is a last-writer-wins store — a ReplacingMergeTree, or anything that dedupes on a version — you must reconcile against the winning version of each row, not whichever copy you happen to read before a merge. In ClickHouse that means argMax(field, version), which gives the same answer as FINAL when versions are unique, you group by the sorting key, and the field is not Nullable (argMax skips NULLs, so it can return an older non-NULL value where FINAL returns the NULL). I checked that on ClickHouse 26.4.2.10 with merges stopped: 100,000 ids across three unmerged parts, zero ids where argMax and FINAL disagreed, while a naive read of the unmerged rows showed three times as many PENDING as there were. Read a pre-merge row and you will manufacture diffs that do not exist and chase ghosts.

Second, be very honest about what your number proves. My headline was that the completion events present in the source reconcile to the destination at about 99.5 percent, every one of them driving a terminal status. That is a real and useful result — but it is coverage plus status, not field-value fidelity. It says the ids exist in the destination and that a landed completion did not leave a record stuck PENDING. It does not say the other fields or the timestamps are right; that is a separate, field-level comparison against the production mapper. Keep the two numbers distinct in the report and never let a coverage percentage quietly stand in for transform correctness. And spend your attention on the residual, not the headline: a gate earns trust by explaining the half-percent that did not reconcile, not by waving the number that did.

6. Read the source the same way the pipeline does

The reconciler has to reuse the exact production parsers and mappers — in my case the same envelope parser and the same column mapper the live job uses. The mapper is the per-column provenance. The moment you re-implement the transform inside the checker, you are no longer validating the pipeline; you are diffing your two implementations against each other, and every place they differ becomes a false positive that looks exactly like a real bug.

Where it landed

In the end the reconciliation is satisfyingly small: one SQL JOIN. The source is read directly — the Iceberg table function pointed at the bronze path with static keys, which auto-discovers the metadata and reads the parquet without going through the catalog's credential delegation at all — and joined against the final-deduped destination, keyed by the correlation id. Source coverage on one side, terminal status on the other, and the residual called out. A sketch, with the envelope parsing and the window bounds left as placeholders:

WITH src AS (                 -- source: read bronze directly, no catalog delegation
  SELECT correlation_id,
         /* parse the completion event out of the envelope */ AS status
  FROM iceberg('s3://.../bronze/<source>', '<key>', '<secret>')
  WHERE event_time >= :from AND event_time < :to
),
dest AS (                     -- destination: the winning row per id
  SELECT correlation_id AS cid,
         argMax(status, updated_at) AS dstat      -- same as FINAL when versions are unique
  FROM reprocess
  GROUP BY correlation_id
)
SELECT
  uniqExact(s.correlation_id)                              AS source_ids,
  uniqExactIf(s.correlation_id, d.cid != '')               AS reconciled,   -- unmatched = '' (join_use_nulls = 0)
  uniqExactIf(s.correlation_id,
              d.dstat IN ('COMPLETED', 'FAILED'))          AS terminal
FROM src s LEFT JOIN dest d ON s.correlation_id = d.cid;

The d.cid != '' test relies on ClickHouse's default join_use_nulls = 0, where an unmatched right side of a LEFT JOIN is filled with the type default — an empty string — rather than NULL. With join_use_nulls = 1 the test has to be d.cid IS NOT NULL, or reconciled silently reads zero.

It gave a clean answer in one pass: about 99.5 percent of the completion events present in bronze reconcile, all terminal, and it pinpointed the day-after connector gap in the same query. Note which check this is: source against destination, at the coverage-and-status depth from section 5. It does not replace the backfill-against-live gate from section 2, which is the one that decides the swap.

One footnote on that read path. Reading the source directly with static keys sidestepped permission failures from the catalog's credential vending, but it trades against the discipline of having one read path everywhere else, and it puts long-lived keys into the reconciler's config. It is correctness-neutral — it reads the same bytes — but it is a choice to make deliberately, not one to back into. The cleaner long-term answer is the one from When Polaris Can't Vend: read through the catalog with vending off and a scoped, read-only key, and keep a single way of reading the lake.

And one limit on scope. The source is a small-files swamp — a single day is thousands of tiny files, and a full-day count just times out from a laptop far from the data — which is why this reconciliation was windowed and sampled source-first rather than run as one full-day scan.

What I am taking away

Three claims, and they are not the same claim: "it ran," "it is correct," and "it is safe to swap." A green run proves the first. A field-level diff against the production mapper proves the second. A no-regression gate against live proves the third, and it is the only one that protects production — so build it before a bad swap teaches you why. The habit I am keeping: every time the gate flags something, ask whether it is my transform or my source. The answer is the difference between fixing a bug and chasing one that was never there.
