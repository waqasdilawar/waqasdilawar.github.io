The distance between my lakehouse and the real one

4 November 2026

Bronze is the raw layer here: Iceberg tables behind a Polaris REST catalog, one per source stream. The backfill reads several of those source streams — I call each one a lane — correlates them, and writes to ClickHouse.

I have a Flink BATCH backfill job that I built and validated entirely against a local lakehouse — Iceberg tables behind a REST catalog, object storage, and a ClickHouse cluster, all sitting on my laptop. It worked beautifully there. The interesting part started the moment I pointed the very same job at the real bronze tables: same code, run from my laptop, reading the real bronze and writing only to my local ClickHouse — never anywhere near the live table.

It did not work. But it did not fail all at once either — it failed one specific mismatch at a time, and each fix unblocked the next, until the job finally planned all four sources and started grinding:

wrong env wiring → wrong table names → wrong catalog → wrong source schema → RUNNING

None of these are really Flink-specific; they are the kind of gotcha you hit whenever a job that "works on my lakehouse" meets the real one.

1. Docker Compose reads ${VAR} from --env-file, not from a service env_file:

This one has cost me a huge amount of time, and it is the most embarrassing because it is so simple.

I had a composed value in my compose file, something like admin:${ROOT_SECRET}. At launch Compose warned me, very politely:

The "ROOT_SECRET" variable is not set. Defaulting to a blank string.

And so my secret resolved to admin: — blank — and the catalog auth failed in a way that looked like everything except the real cause.

The gotcha is that there are two different mechanisms that look like the same thing. A service-level env_file: injects variables into the container's environment at runtime. It does not feed ${VAR} interpolation in the compose file itself. That substitution happens much earlier, before any container exists, and it is fed by the shell, by a .env in the project directory (next to the compose file), or by --env-file on the command line. If your composed values reference secrets, you have to pass --env-file, otherwise the interpolation quietly becomes blank and you go chasing the wrong thing.

2. Hard-coded resource names are a portability tax

My four source classes had the local table names baked in — the names from my local fixtures. Against the real catalog those names are different, so naturally: table not found.

The fix is boring and correct: make the names env-configurable. The small thing worth sharing is how — I added an overloaded constructor that takes an explicit table name, where a blank value falls back to the old default. That way the streaming callers and the other callers, which already pass nothing, stay completely untouched, and only the backfill resolves names from the environment. When the same code has to run against local fixtures and a real catalog, parameterize the names but keep the default path intact, or something will break for a caller you had forgotten about.

3. "Table does not exist" usually means "wrong warehouse," not "missing table"

This is the lesson hiding behind number 2. After I made the names configurable, I still got table-not-found — and the real cause was not the table at all. The bronze tables live under a different warehouse in the real catalog than the one I had on my laptop. The REST catalog was answering me honestly: in this warehouse, that table does not exist.

There was also a trailing-comma typo in my warehouse value that would have broken the lookup on its own, even with the right name. So when an Iceberg REST catalog (we use Polaris) gives you a NoSuchTableException, do not immediately chase the table name. Confirm the warehouse and namespace resolution first. The catalog is rarely lying; it is usually pointing at the wrong shelf. I later reproduced it on Polaris 1.6.0: the same loadTable through a different catalog, or through a prefix with a trailing comma, comes back 404 NoSuchTableException: Table does not exist.

4. Bronze is an envelope, not flat columns

My local fixtures had a flat schema, so my reader pruned and read a top-level column like created_at. Against real bronze I got (the field name is changed here):

Cannot find field 'created_at' in struct: correlation_id, event_time, payload, _kafka_metadata

The real bronze is a filebeat-style envelope. The actual record is a JSON string sitting inside payload, and the event time lives in event_time, not as a flat created_at at all. My reader had been written for a shape that only ever existed locally.

The fix that I am happy about: instead of writing a second, batch-only reader that knows how to unwrap the envelope, I made the batch source prune on event_time and parse payload using the same parser the streaming path already uses — the one that unwraps the envelope every day in production. The lesson is the lockstep, not the unwrap. The moment you keep two readers for the same data — one for streaming, one for batch — they will drift, and your batch backfill will quietly disagree with your stream. Reuse the streaming parser in batch and the envelope handling stays honest by construction.

As a small bonus, this fixed my local lane too, which had been broken since we migrated to the envelope shape and I had simply not noticed.

5. When lanes serialize, do not assume you are short on slots

This is the one whose real cause I got wrong twice before I saw it.

With everything resolved, the job planned all four sources and started reading — and one lane ran while the other three sat in CREATED. It looked stuck, though it was not: bytes were climbing and there were zero exceptions, so it was progressing, just one lane at a time. The obvious diagnosis was a slot shortage, so I did the obvious thing — I tore the whole stack down to just the Flink job and one ClickHouse node, and handed Flink roughly two dozen slots.

The lane still ran alone. Three sources in CREATED, zero slots free, all that capacity sitting right there.

The real reason had nothing to do with capacity. I was building each source stream with Iceberg's IcebergSource.Builder.buildStream(env), which infers a batch source's parallelism from its split count when table.exec.iceberg.infer-source-parallelism is true (the default, capped at 100). So the first lane sized itself to its split count, inflated to thirty-something subtasks on its own, and ate every slot. The others had nothing left to start on. Every TaskManager I had added was only raising one lane's parallelism; it was never buying me concurrency across lanes.

The fix was a one-line swap per source. Building the stream through the plain env.fromSource(...) instead makes the source honor parallelism.default rather than inferring its own. (Setting table.exec.iceberg.infer-source-parallelism to false would have let me keep buildStream.) I set parallelism.default to a modest six, and that is exactly what happened — all four lanes running together at six apiece, twenty-four slots full, the serial single-lane grind simply gone. The source stage drops from the sum of the lanes to the slowest single one.

The "one-line swap" was not quite one line, though. Moving to fromSource sent three more bills, and they are the kind you only meet at this point:

  • Type erasure. fromSource needs the record TypeInformation handed to it explicitly, because the generic is erased at the call site. For Flink's internal row type that is InternalTypeInfo.of(rowType) — without it the job failed at build time with a type-inference error.
  • Slow split enumeration from a laptop far from the data. Enumerating four sources' splits took longer than the default client timeout (client.timeout, 60 s), so the submit failed before the job ever ran. Raising it fixed it.
  • Starved network buffers. Four concurrent shuffles need far more network memory than one serial lane, so I had to raise taskmanager.memory.network.fraction before the concurrent run would schedule at all.

None of these are interesting on their own. The lesson is that a conceptual one-line fix often drags a tail of secondary fixes behind it, so budget for them. And the headline still stands: when your lanes serialize, do not reach for more slots first — check whether a source is sizing its own parallelism, because one operator that inflates to its split count starves every sibling no matter how much capacity you add.

Two smaller ones, while I have them

A row-level time filter did not shrink my day-partitioned scan. I cut my read down to a single hour expecting the file scan to drop twenty-four times. It did not: the same day's files were opened. Iceberg can skip files on per-column min/max as well as on partitions, so either my hour filter ran after the source instead of inside it, or every file's event_time range spanned the day. The downstream work drops nicely; the source scan does not. Push the filter into the scan, and partition at the grain you actually query.

Not every alarming log line is a failure. Throughout the run I kept seeing:

Forbidden: not authorized for op REPORT_READ_METRICS

It looks like an auth failure that should stop everything. It is the Iceberg client failing to post a scan report back to the catalog — the client catches it and the read carries on. Learn which of your scary log lines are load-bearing and which are just noise, or you will chase the wrong one.

The wall I was sure was the network — and was not

For a while the job kept dying on a read that truncated mid-file, and I was certain it was a flaky network. It was not. It was a deterministic cap — a proxy in front of the object store was cutting every GET response at about 12.5 MiB. The proof is the kind you cannot argue with: the same file, retried, truncated at the identical byte — 13,107,196, four bytes short of 12.5 × 1,048,576. Random network loss never lands on the same byte twice. One earlier truncation at a different offset had thrown me off — that one really was a transient flap — but once I set it aside, the cap was dead consistent. I had argued myself out of the obvious explanation; the bytes argued me back.

The fix was not more parallelism and not a better network. It was to read each file in smaller pieces — set the split size (split-size, or the table's read.split.target-size, 128 MB by default) below the cap, so files are read as row-group-aligned sub-ranges. The truncations went to zero. (A single row group bigger than the cap cannot be split that way.)

And that bought me the next wall, on one of the two heavy lanes. With small splits, that source's GET count exploded — and it stalled, every reader hung waiting for response bytes that never came. This was not the size cap; the reads were now small. It was the data layout. The table metadata told the whole story: about sixteen thousand data files for twenty-one gigabytes — roughly 1.3 MB per file — because a streaming sink had been committing a handful of tiny files on every checkpoint for thousands of commits. A small-files explosion. The number of GETs is bounded by the file count, not by my split size, so there is no split setting that escapes it. The real fix for that lane is compaction — bin-pack those thousands of tiny files into a few large ones — and compaction has to read every one of those small files, so it must run next to the data, not from a laptop.

So two real limits, not one, and the lane that has both a few large files and about sixteen thousand tiny ones is the only one that trips both. That is the part I got wrong early: I tried to collapse it into a single mechanism, and it genuinely was two.

Where it landed

Rather than wait on the compaction, I added a flag to skip the two heavy sources and read only the two light ones. That ran clean, end to end — envelope read, correlation, and sink, the whole spine — and landed its first real result in the local ClickHouse: an hour of correlated rows, the first time real data has made it all the way through to a local table. The small-files lane still needs its compaction fix before it can be backfilled, but the pipeline itself is now proven against real data.

For the record, here is every fix it took, in the order I found them — which is also a fair map of where the time went:

  • Lanes serialized because a source inferred its own parallelism → build through env.fromSource, which honors parallelism.default.
  • fromSource type erasure → hand it the TypeInformation explicitly (InternalTypeInfo.of(rowType)).
  • Job init timed out enumerating splits → raise client.timeout.
  • Concurrent shuffles starved the network buffers → raise taskmanager.memory.network.fraction.
  • A ~12.5 MiB per-GET size cap truncating large files → set the split size below it. This was the real one.
  • A genuine transient mid-read close → a fixed-delay restart strategy plus connector retries, as a second line.

What I am taking away

The whole exercise was one lesson wearing several costumes. The early ones were small, findable code mismatches — env wiring, names, warehouses, data shapes, and the subtle one of where a source decides its own parallelism. The last one was not in my code at all, and it was the one I was slowest to read correctly: what looked like a flaky network was a deterministic proxy cap, and what looked like a rate limit was a small-files problem in disguise. The laptop could never have shown me any of those last few — there was no proxy in the path, and no years-deep streaming table to fetch.

If you are about to point a local job at real data: keep the harness read-only against the real data and write only to your local sink; fix one specific failure at a time; do not assume serial lanes mean too few slots; set a restart strategy before a flaky link does it for you; and when a read keeps failing, read the bytes before you blame the network — a truncation that lands on the same byte twice is telling you something a retry will never fix.

The Compose and Polaris behaviour above were reproduced in a lab (Docker Compose v5.6, Polaris 1.6.0); the Flink parallelism and split-size sections are my own run plus the Flink and Iceberg docs.
