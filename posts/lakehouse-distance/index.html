The distance between my lakehouse and the real one

4 November 2026

A local lakehouse proves your logic. It does not prove your assumptions about the real one, and those fail in a predictable order: where the data is, what shape it has, how the engine plans the read, and what sits on the wire between you and the bytes. You can close the first two before you leave the laptop. The last two you have to design for.

The job is a Flink BATCH backfill. It reads several bronze source streams (I call each one a lane), correlates them, and writes to ClickHouse. Bronze is the raw layer: one Iceberg table per stream, behind a Polaris REST catalog. I built and validated the job against a local copy of that stack, then pointed the same code at the real bronze tables. The harness was read-only against real data and wrote only to a local ClickHouse. That constraint is what made it safe to iterate quickly against production data, and I would set it up the same way again.

The job did not fail once. It failed one layer at a time, and each fix exposed the next.

1. Identity: the catalog answers the question you asked

The first real failure was NoSuchTableException. The table names were baked in from my local fixtures, so I made them configurable, and the error stayed. The real cause was one level up: the bronze tables live in a different warehouse in the real catalog than in my local one. Polaris was answering correctly. In the warehouse I asked about, that table does not exist. I reproduced it on Polaris 1.6.0: a loadTable through the wrong catalog, or through a malformed prefix, comes back as 404 NoSuchTableException: Table does not exist, the same as a table that really is missing.

The lesson: a table's identity is the whole tuple of catalog, warehouse, namespace and table, not the table name. Treat that tuple as one piece of configuration, check it before anything else, and when the catalog says "not found", check the resolution before you check the table.

2. Contract: my fixtures encoded a schema that no longer existed

With the right warehouse, the read failed on shape (field name changed here):

Cannot find field 'created_at' in struct: correlation_id, event_time, payload, _kafka_metadata

My fixtures had a flat schema. Real bronze is an envelope: the record is a JSON string inside payload, and event time is a top-level event_time. My batch reader had been written for a shape that only ever existed on my laptop.

The obvious fix was a batch-specific reader that unwraps the envelope. I did not write one. The batch source now prunes on event_time and parses payload with the same parser the streaming job runs in production every day. Two readers for the same data will drift, and when they do, the backfill quietly disagrees with the stream it is meant to repair. One decoder keeps them in step.

The detail that worried me most: the local lane had been broken ever since bronze moved to the envelope, and nothing had told me. Hand-written fixtures go stale without anyone noticing. Generate them from the real table schema, or they will keep proving a contract nobody honours any more.

3. Execution: more capacity did not buy concurrency

With all four sources planned, one lane ran and the other three sat in CREATED. It was making progress, with bytes climbing and no exceptions, but serially. I read that as a slot shortage, cut the stack down to the Flink job and one ClickHouse node, and gave Flink about two dozen slots. One lane still ran alone, with zero slots free.

The cause was how I built the sources. IcebergSource.Builder.buildStream(env) infers a batch source's parallelism from its split count when table.exec.iceberg.infer-source-parallelism is on (the default, capped at 100). The first lane sized itself to thirty-something subtasks and took every slot. Each slot I added only raised that one lane's parallelism.

Building through env.fromSource(...) makes the source honour parallelism.default instead. (Turning the inference flag off would do the same.) At six per source, all four lanes ran together on twenty-four slots, and the source stage dropped from the sum of the lanes to the slowest one. The change also made the job's real resource needs visible, which the serial run had hidden: it needed explicit TypeInformation for the erased row type, a longer client.timeout for split enumeration from far away, and a larger network-buffer fraction for four concurrent shuffles. Budget for that tail whenever a fix changes the shape of a job.

Two smaller planning lessons from the same run:

  • A row filter is not a scan filter. Narrowing the read to one hour of a day-partitioned table opened the same day's files. Either the predicate ran after the source rather than in it, or every file's event_time range covered the whole day. Downstream work shrank and the scan did not. Push predicates into the source, and partition at the grain you query.
  • Know which errors are load-bearing. A steady stream of Forbidden: not authorized for op REPORT_READ_METRICS looks like an auth failure. It is the Iceberg client failing to post a scan report back to the catalog. The client catches it and the read carries on.

4. The physical path: two limits that looked like one

Next, reads started truncating mid-file. I was sure it was a flaky network. It was a proxy in front of the object store that cut every GET response at 12.5 MiB. The evidence was determinism: the same file, retried, truncated at the same byte every time, 13,107,196, four bytes short of 12.5 × 1,048,576. Random loss does not land on the same byte twice. One earlier truncation at a different offset really was a transient fault, and it had talked me out of the obvious explanation for a while.

The fix was to read each file in pieces smaller than the cap: set split-size (or the table's read.split.target-size, 128 MB by default) below it, so files are read as row-group-aligned sub-ranges. Truncations went to zero. A single row group larger than the cap would still fail, so the cap is now a constraint on how bronze is written, not just on how it is read.

Small splits then exposed the second limit, on one of the two heavy lanes. Its GET count exploded and its readers stalled waiting for bytes. The table metadata explained it: about sixteen thousand data files for twenty-one gigabytes, roughly 1.3 MB each, left by a streaming sink committing a few small files on every checkpoint. The request count is bounded by file count, not split size, so no read setting fixes it. The fix is compaction, and compaction has to read every one of those files, so it belongs next to the data, not on a laptop.

That lane has both a few files larger than the cap and thousands of tiny ones, so it was the only lane to hit both limits. I spent too long trying to explain both symptoms with one mechanism.

Where it landed

Rather than block on compaction, I added a flag to skip the two heavy lanes. The two light lanes then ran end to end, through the envelope read, correlation and the sink, and real data reached a local table for the first time. The pipeline is proven against real data; the small-files lane waits on compaction.

What I would make standard

  • Read real, write local. A harness that is read-only against production data and writes only to a local sink lets you iterate against reality with no blast radius.
  • Derive fixtures from the real schema, and share decoders. Stale fixtures and duplicated parsers are the same failure: two descriptions of the data that are free to disagree.
  • Never let a source size itself in a multi-source job. Inferred parallelism is reasonable for one source. With several, it turns capacity into one lane's parallelism instead of concurrency.
  • Classify failures before you fix them. Deterministic means a limit; random means a fault. Retries and restart strategies are for faults. They hide limits.
  • Read the table's layout before you plan the backfill. File count and average file size come straight from the metadata. They tell you whether the read is feasible at all, and whether compaction has to come first.

The Polaris behaviour above was reproduced on Polaris 1.6.0; the Flink parallelism and split-size sections come from my own run plus the Flink and Iceberg docs.
