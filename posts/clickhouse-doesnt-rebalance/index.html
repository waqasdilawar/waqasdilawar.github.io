ClickHouse Doesn't Rebalance: Sharding Keys, Skew, and the Cost of Adding a Shard

3 November 2026

ClickHouse does not move a row to another shard after it is written. So the sharding key decides three things at once: whether your joins stay local, whether one shard gets hammered, and how much work it is to add a shard later. In my production cluster we picked tenant as the key and accepted skew, because the tables we join share that key. This post is what I tested to check that choice, and what I found when I asked the next question: what happens when we add a shard?

First, how a row gets placed. A ClickHouse Distributed table stores no data. It sits in front of one local table per shard, sends each inserted row to one shard, and sends each query to all of them. Which shard a row lands on is decided by the sharding key: ClickHouse takes the remainder of the key divided by the total shard weight. With two equal shards and cityHash64(tenant_id), that is cityHash64(tenant_id) % 2.

The lab

ClickHouse 26.4.2.10, two shards with two replicas each, three Keeper nodes, all in Docker on a laptop. One events table sharded by cityHash64(tenant_id), 1,000 rows across 20 tenants. Every number below is real output from that lab.

INSERT INTO demo.events
SELECT now(), number % 20, 'click', '{}' FROM numbers(1000)
SETTINGS distributed_foreground_insert = 1;

-- rows on one replica of each shard
SELECT hostName() AS node, count() AS rows
FROM clusterAllReplicas('local_cluster', demo.events_local)
WHERE hostName() LIKE '%replica1'
GROUP BY node ORDER BY node;
-- ch-shard1-replica1  600
-- ch-shard2-replica1  400

Inserts into a Distributed table are sent to the shards in the background by default, so a count right after the insert can come back short. distributed_foreground_insert = 1 makes the tests deterministic.

Keep each tenant together: local joins, and skew

With a tenant key, all of a tenant's rows live on one shard. That buys two things.

First, a query that filters on the tenant only needs one shard. Turn on optimize_skip_unused_shards and ClickHouse asks only that shard. You can see it in the query log. One catch: the server that starts the query reads its own shard locally, and that read never shows up as a remote query. Set prefer_localhost_replica = 0 to force every shard read over the network, and the difference is clear:

-- started on shard 02, tenant 0 lives on shard 01
default                       shard 01 asked, shard 02 asked
optimize_skip_unused_shards   shard 01 asked

Second, joins. I made a tenants table (20 rows, a plan per tenant) with the same sharding key, so each tenant's plan sits on the same shard as its events. With distributed_product_mode = 'local', each shard joins only its own rows and nothing big crosses the network:

SELECT t.plan, count() AS events
FROM demo.events AS e
JOIN demo.tenants AS t ON e.tenant_id = t.tenant_id
GROUP BY t.plan
SETTINGS distributed_product_mode = 'local';
-- pro   500
-- free  500     (correct)

The price is skew. One big tenant sends 3,000 more events, and they all land on its shard:

shard 01    600
shard 02   3400

Every read and write for that tenant now hits one shard while the other idles.

Spread rows out: balance, and wrong joins

The obvious fix for skew is rand() as the key. Every shard gets about the same rows, and the tables are no longer co-located. To see what that does to a join, I built tenants_rand: the same 20 rows, placed at random across the two shards, and ran the same local join against it. With the big tenant's 3,000 rows included, the right answer is 3,500 / 500:

pro   3300
free   150     (truth: 3,500 / 500, and no error)

A tenant's plan only matches events that happen to sit on the same shard. Here 6 of 10 pro tenants (the big one among them) and 3 of 10 free tenants got lucky. The rest silently dropped out of the answer.

To be fair to ClickHouse, you have to ask for this. The default distributed_product_mode is deny, which refuses the query:

Code: 288. DB::Exception: Double-distributed IN/JOIN subqueries is denied
(distributed_product_mode = 'deny')

I turned that protection off to show what it protects you from. The correct way for non-co-located tables is distributed_product_mode = 'global' (or GLOBAL JOIN): ClickHouse first copies the whole right-hand table to every shard, a broadcast join. It returned 3,500 / 500. That's fine for a 20-row table and expensive for a big one. The docs' distributed join FAQ still reads "As of 2025, ClickHouse does not perform shuffle joins", and I found nothing newer that replaces it. There is an experimental distributed planner (make_distributed_plan) that can, but it is off by default, so for tables that aren't co-located, broadcast is what you get.

Group-bys change too. With a tenant key, each tenant's groups live on one shard, so each shard sends back only its own tenants. With rand(), every shard sends a partial result for every tenant, and one server merges them all. When you group by the sharding key itself, ClickHouse uses this (optimize_distributed_group_by_sharding_key, on by default) and skips the merge on that server.

So the key choice is a trade-off:

KeyYou getYou pay
cityHash64(tenant_id)Local joins on tables with the same key, one-shard filters, small group-by resultsSkew when tenants differ in size
rand()Even shardsJoins need a broadcast; big group-bys merge everything on one server

We chose the first. Some shards are heavier and we live with it, because correct local joins matter more to us than perfect balance. If you do the same, give every table you join the same key.

Then you add a shard

The ClickHouse docs say it plainly: "ClickHouse doesn't support automatic shard rebalancing." Add a third shard and nothing moves. Old rows stay where they are, and new rows follow the key.

With a tenant key, that is already a split. The key now sends some tenants to the new shard, so their old rows sit on one shard and their new rows land on another. How many? With modulo, most of them:

SELECT round(100 * countIf(cityHash64(number) % 2
                         != cityHash64(number) % 3) / count(), 1)
FROM numbers(1000000);
-- 66.6   (2 → 3 shards)
-- 80.1   (4 → 5 shards, same query with % 4 and % 5)
-- 83.3   (5 → 6 shards)

Going from N−1 to N shards moves 1 − 1/N of the keys, so the bigger the cluster, the worse each step. Moving the data yourself means moving most of it.

The docs offer an easier way. The Distributed engine page says you don't have to move old data: "you can write new data to it by using a heavier weight". That's true for random placement, where nobody cares which shard holds a row. With a tenant key it doesn't fix the split. With weights 1, 1, 2 the total weight is 4: remainders 0 and 1 keep their old shard, 2 and 3 go to the new one. Half of all new writes go to the new shard, which is the point of the heavier weight, but 477 of 1,000 tenant IDs now map to a different shard than their old rows.

The wrong answer with no error

Split tenants also give wrong answers. I made a second Distributed table over the same local tables with a changed key, cityHash64(tenant_id) + 1, which flips every tenant to the other shard. Nothing was moved. Then I asked for tenant 2, the big one from the skew test:

CREATE TABLE demo.events_newkey AS demo.events_local
ENGINE = Distributed('local_cluster', 'demo', 'events_local',
                     cityHash64(tenant_id) + 1);

SELECT count() FROM demo.events_newkey WHERE tenant_id = 2
SETTINGS optimize_skip_unused_shards = 1;
-- 0

SELECT count() FROM demo.events_newkey WHERE tenant_id = 2;
-- 3050   (50 original rows + the 3,000 hot-tenant rows)

Zero rows, and no error. Skip unused shards trusts the key, asks only the shard where tenant 2 should be, and its rows are somewhere else. The settings docs warn about exactly this:

Assumes that the data is distributed by sharding key, otherwise a query yields incorrect result.

Local joins break the same way. Any half-finished resharding puts you here, so turn those optimizations off, or route queries to the old table, until the move is done and verified.

A better key: jumpConsistentHash

ClickHouse has jumpConsistentHash(key, buckets), the jump consistent hash from Google. Use it in the sharding key, with the shard count as the second argument, and adding a shard moves about 1/N of the keys, all of them to the new shard:

-- keys that moved between two OLD shards when going from 2 to 3
SELECT countIf(jumpConsistentHash(cityHash64(number), 2)
                 != jumpConsistentHash(cityHash64(number), 3)
               AND jumpConsistentHash(cityHash64(number), 3) != 2)
FROM numbers(1000000);
-- 0

I also used it as a real sharding key, jumpConsistentHash(cityHash64(tenant_id), 2), and all 20 tenants landed on the shard it predicted. Three caveats:

  • The shard count is part of the key. Adding a shard still means changing the key and moving the affected rows yourself. There are just far fewer of them.
  • The Distributed engine still takes the result modulo the total weight, so keep every shard at weight 1 and the bucket count equal to the shard count.
  • Jump hash adds and removes buckets at the end only. You can't take out a shard in the middle.

If you shard by a key, decide this on day one. Changing the key later is the same migration you were trying to avoid.

Moving the data, and a recipe that loses it

You will move rows yourself, and inserts keep arriving while you copy, so it is easy to copy some rows twice and miss others. A recipe you will find in rebalancing guides: re-insert a partition from the overloaded shard through the Distributed table, then drop that partition on the source shard. I tried it:

-- trap table: same key, partitioned by day, 1,000 rows (600 on shard 01)
INSERT INTO demo.trap
SELECT * FROM remote('ch-shard1-replica1', demo.trap_local, 'default', '<password>')
WHERE d = '2026-01-01'
SETTINGS distributed_foreground_insert = 1;

-- on ch-shard1-replica1
ALTER TABLE demo.trap_local DROP PARTITION '2026-01-01';

SELECT count() FROM demo.trap;
-- before: 1000   after: 400

The rows went back into the same table. Every row whose key still points at shard 01 landed in the same partition on shard 01, and the drop deleted them along with the originals. Here the key hadn't changed, so all 600 were lost. After a real key change, the rows whose key still points at the source shard would come back and be lost: about a third of them for the modulo 2 → 3 change above. Nothing warns you.

What works:

  1. Create new local tables and a new Distributed table with the new key or shard count.
  2. Copy old partitions that no longer change, one at a time, through the new Distributed table. (Moving whole partitions with DETACH/ATTACH is faster, but only works when the key hasn't changed. After a key change, one partition's rows belong to several shards.)
  3. Compare counts per partition between old and new.
  4. Cut readers over when the counts match, and handle the still-changing recent partitions last.
  5. Only then drop the old partitions.

Some teams don't move data in place at all. Contentsquare wrote in 2022 that they built resharding around their daily S3 backups: bring up a cluster with the new shard count, restore the backup into it, and re-split the data there with clickhouse-copier, so production is never the source of the copy. (clickhouse-copier is no longer part of ClickHouse, so today that step would be an INSERT … SELECT or a backup tool.) The scaling guide calls INSERT … SELECT into a new cluster the last resort: slow on very large data, and heavy on I/O for the source cluster.

Replicas: safety first, then readers

Sharding spreads the data over more machines. Replication keeps a copy of the same data on more than one. You turn it on per table with ReplicatedMergeTree: when one replica writes a part, it records that in Keeper, and the other replica fetches the part from it. Keeper holds the log, never the rows.

I stopped one replica of shard 01 and inserted 1,000 rows through the Distributed table. The write was accepted.

By default an insert waits for one replica. If that server's disk dies before the copy is made, those rows are gone. insert_quorum makes the insert wait for more copies, and its failure mode is worth knowing. With the replica still stopped, I inserted 10 more rows straight into the shard's local table:

INSERT ... SETTINGS insert_quorum = 2, insert_quorum_timeout = 5000
Code: 319. Unknown quorum status. The data was inserted in the local replica
but we could not verify quorum. Reason: Timeout while waiting for quorum.

The client saw an error, but the rows were written. You only get this error if the stopped replica still looks alive to Keeper, as it did here seconds after docker stop. Once Keeper has noticed, the insert fails up front because too few replicas are live, and nothing is written. Then I started the replica again. By the time it answered its first query it had caught up, including the 10 quorum rows:

ch-shard1-replica1   1210
ch-shard1-replica2   1210
ch-shard2-replica1   3800
ch-shard2-replica2   3800

A client that blindly retries a quorum error can write the rows twice. Retry the exact same block so insert deduplication can drop it (it only remembers recent blocks, see replicated_deduplication_window), or set insert_deduplication_token, or check before retrying.

The second job of a replica is reads: a query goes to one replica of each shard, so more replicas means more queries in parallel. That's the pattern I like for BI dashboards and AI agents that fire lots of queries. Don't add shards for them. Add a replica to each shard and point them at those replicas only, with a second cluster definition:

<remote_servers>
  <agents_cluster>
    <shard><replica><host>ch-shard1-replica2</host>...</replica></shard>
    <shard><replica><host>ch-shard2-replica2</host>...</replica></shard>
  </agents_cluster>
</remote_servers>

A Distributed table on agents_cluster returned the full count, and the query log showed only ch-shard1-replica2 and ch-shard2-replica2 did the reading. Two catches: those replicas still take every write, because they are full copies, and they can lag behind the replica that took the insert, because replication is asynchronous.

Debugging queries I keep

-- where do a tenant's rows live?
SELECT hostName(), count()
FROM clusterAllReplicas('local_cluster', demo.events_local)
WHERE tenant_id = 2 GROUP BY hostName();

-- is a shard heavier?
SELECT hostName(), sum(rows), formatReadableSize(sum(bytes_on_disk))
FROM clusterAllReplicas('local_cluster', system.parts)
WHERE active AND table = 'events_local' GROUP BY hostName();

-- background inserts stuck?
SELECT database, table, data_files, error_count, last_exception
FROM clusterAllReplicas('local_cluster', system.distribution_queue);

-- replication healthy?
SELECT hostName(), table, is_readonly, queue_size, absolute_delay
FROM clusterAllReplicas('local_cluster', system.replicas);

-- which servers ran my query? (SYSTEM FLUSH LOGS on every node first)
SELECT hostName(), is_initial_query, read_rows
FROM clusterAllReplicas('local_cluster', system.query_log)
WHERE log_comment = 'my-tag' AND type = 'QueryFinish';

Before you shard

One ClickHouse server handles a lot. Make it fast first: a good sort key, the right types, big insert batches. Then a bigger machine. The docs give two reasons to shard: the data is too large for one server, or one server is too slow. Add replicas for safety and for readers. Add shards when one machine really isn't enough, and when you do, choose the key you join and filter on most, and think about how you will add the next shard before you add the first.
