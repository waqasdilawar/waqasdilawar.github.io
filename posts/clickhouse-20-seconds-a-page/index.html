20 seconds a page: where ClickHouse was really spending the time

4 November 2026

We moved a customer-facing analytics API from a legacy batch warehouse to ClickHouse. It serves dashboards, a paged list of records, and a detail view, and it reads tables that keep one row per version of a record (ReplacingMergeTree by updated_at), folded to the latest version at read time. Day partitions on event time; the sorting key is account and record id, not time.

The numbers matched on day one — within 0.3% of the old warehouse on a day for the largest clients. The speed did not. One page of the list for the largest client took about 20 seconds, whatever the window, the page number or the API version; the old warehouse took 1 to 6. Under load, a page of 15 rows used 25 to 35 GB of memory.

The fixes are easy to list. The method is what I would reuse: the cause was different on every screen, and two of them were not where we first looked.

The short version

  • Measure the statement, not the response. system.query_log gives duration, rows read, bytes and memory per statement — but only for the node you are connected to. Use clusterAllReplicas, and tag every statement with log_comment so you know which screen it came from.
  • If a small client costs the same as a large one, the cost is not the data. In our case it was the statement text.
  • Compare what a statement reads with what it returns. A page that reads the whole day several times has a shape problem, not a data problem.
  • Let EXPLAIN indexes = 1 tell you how many parts were opened. FINAL was opening every partition.

Three questions that found everything

  1. Does a small client cost the same as a large one? Run the same screen for a client with a hundred records a day and one with a million. If both pay the same, the time is not in the data.
  2. How much does the statement read compared with what it returns? read_rows against the client's real row count for the window. Then run day, week, month, page 1 and page 21. Does the read grow with the window, the page, or neither?
  3. How many parts and partitions are opened? EXPLAIN indexes = 1, with and without a bound on the partition.

Every case below came out of one of those three.

Case 1: the statement text was the cost

One page for a medium client took 13.6 s. A client with about a hundred records a day paid the same 13 s as one with a million. That was the giveaway.

The page view was about 33,000 characters. It chose the time slice inside the SQL, with a sub-select that the rest of the view referenced eight times, and ClickHouse analysed it again each time — a non-MATERIALIZED sub-select or CTE is inlined at every reference, so it is analysed and run eight times, not once (newer versions have MATERIALIZED CTEs behind enable_materialized_cte if you can't move the decision out). To choose the slice, it also folded the client's whole last day just to count whether the last hour could fill a page. Most of the 13.6 s went to analysing the statement; reading the data took about half a second.

The fix was to stop making ClickHouse decide. The application computes the slice with plain arithmetic — the hour next to the cursor, or the last real hour of the window — and passes it as literal values. Two statements run in parallel: the total comes from an hourly rollup (0.03 s), and the page folds only that one hour (1.7 s for the largest client). If the hour cannot fill the page, the request falls back to the wide path. In shape (not the real queries): statement A is count() from the hourly rollup for the window; statement B is the page from that one hour, FINAL bounded to that hour's partition.

Every client on that path went from 13–19 s a page to 1.5–2.8 s. The largest client's two months went from 22.8 s to 3.1 s, reading a third of the rows with a sixth of the memory. And the answer did not change: 252 of 254 requests were identical row by row against the old path; the other two were invalid inputs that now return 400 instead of 500.

Case 2: FINAL opened every partition

Here's the part that surprised me. With FINAL and a time range, EXPLAIN showed one table opening 150 of 150 parts. With a condition on the partition id, it opened 19. Another screen opened 233 of 233, against 34.

I reproduced it on ClickHouse 26.4.2.10 with the same layout — ReplacingMergeTree(updated_at), PARTITION BY toDate(event_time), ORDER BY (account, record_id), 30 day partitions, merges stopped — and one day's window for one account:

query parts opened granules after primary key
no FINAL, time range 1 / 30 1 / 12
FINAL, time range 30 / 30 30 / 360
FINAL, time range + _partition_id bound 1 / 1 (the bound selects the part before the index runs) 1 / 12 
SELECT ... FROM t FINAL
WHERE account = 7 AND event_time >= '2026-06-10' AND event_time < '2026-06-11'
  AND _partition_id IN ('20260610')   -- pad by the days a late version can arrive

This is not a bug in your query. When the partition key columns are not covered by the sorting key, a newer version of a row can sit in another partition, and pruning before FINAL could skip the row that should win. ClickHouse 26.3 fixed that by not pruning partitions under FINAL for this layout; 26.5 added defer_partition_pruning_after_final (set it to 0 to get pruning back, with the same risk). Our test container ran 24.8, which still pruned, so the tests were fast and production was not. The integration tests now run on the production version.

The fix was to bound FINAL ourselves with a padded _partition_id range: versions of a record arrive within a known number of days, so padding the window by that much keeps every candidate winner in range. One dashboard went from 6.55 s to 1.72 s and from 1.31 GB to 0.10 GB of memory. One table went from 22.4 s and 73 M rows to 0.95 s and 10 M rows.

The alternative we rejected was do_not_merge_across_partitions_select_final = 1. It was faster still, and it counted 2% of records twice — the ones whose versions sat on two days.

Case 3: a page read the whole day several times

The other list took about 20 s a page for the largest client, whatever the window or page number. A newer cursor API gave the same time. The query log said the client had 4.4 M rows that day, and the page read 20.3 M rows, 2.3 GB and 5.2 GB of memory. The total was not the problem: it came from the rollup in 18 ms.

Time is not in the sorting key. Inside a day, an account's rows are ordered by record id, so the rows of one hour are spread over the whole day. Every page read the day, and read it several times. A cursor only chooses which 15 rows come back after the same scan, so page 21 cost the same as page 1.

The test that showed the way out: on production, counting the client's rows for the day took 1.1 s, and folding only the status per record and taking the newest 15 keys took 1.8 s. The scan itself was cheap; the shape of the read was not.

So: keys first, from narrow columns, then the wide columns for those 15 keys, plus the same hour-first slicing as Case 1. One client's month went from 35 s on the old warehouse and 9.3 s on ClickHouse to 2.1 s; another's from 46 s and 9.7 s to 2.1 s.

Case 4: one OR branch outside the key

Opening one record took 1.2 to 1.7 s inside ClickHouse. The statement found the row two ways — by record id, or by an external id — joined with OR. The external id is not in the sorting key, and one branch the index cannot use makes the whole OR unusable for the index, so ClickHouse read the account's whole window. In the lab (26.4.2.10, 3 M rows, one account of 1.5 M):

condition rows read
account = a AND record_id = r 8,192
account = a AND (record_id = r OR ext_id = x) 1,500,864
account = a AND record_id IN (r, r_of_x) 16,384
account = a AND (record_id = r OR record_id = r2) 16,384

The OR itself is fine when both branches are in the key. The fix was two small lookups for the keys, then one IN (ids): 0.45 s inside ClickHouse, and 38 of 38 details identical to the old path.

The decoder

symptom cause fix
A small client is as slow as a large one Statement analysis, not data (a sub-select referenced many times) Decide in the application; pass literals
A page reads many times its client's rows Time not in the sorting key; every page scans the day Keys first from narrow columns, then wide columns for those keys; slice by the hour the page needs
FINAL + time range opens every partition Partition key not in the sorting key (26.3+ stops pruning under FINAL) Bound FINAL with a padded _partition_id range; prove it with EXPLAIN
One lookup reads the account's whole window OR with a branch outside the sorting key Look up the keys, then one IN (ids)
Statements keep running after the client gave up No limits on the API's user; over HTTP, cancel_http_readonly_queries_on_client_close is off by default on self-managed ClickHouse (Cloud turns it on) A settings profile for the API user (max_execution_time, max_memory_usage, max_concurrent_queries_for_user) and that setting on

Under load, one test left 46 statements running after their clients had gone, the longest for over 18 minutes. That last row is the one I would set up first next time.

Nothing here needed new hardware. Every fix came from a measurement, and every fix was checked row by row against the old path before it shipped. Speed without parity is not a fix. For point lookups by a high-cardinality id, the bloom skip index from Finding one row fast is the other half.

The production numbers above are ours, observed on ClickHouse 26.3. The FINAL and OR tables were reproduced on ClickHouse 26.4.2.10; the statement-analysis cost was not (a small lab only showed the direction).

Where this comes from

  • ClickHouse 26.3 changelog, PR #98242: partition pruning is no longer applied under FINAL when the partition key columns are not covered by the sorting key.
  • ClickHouse 26.5 changelog, PR #104705: defer_partition_pruning_after_final.
