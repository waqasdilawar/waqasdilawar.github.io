When Polaris Can't Vend: What Actually Guards ClickHouse Reads on OCI

25 June 2026

Quick context. An Iceberg table is Parquet files plus metadata in object storage, and Polaris is the catalog that tells an engine where that metadata lives and who may load it. ClickHouse loads the table from Polaris, then reads the manifests and Parquet from storage itself — with a key from its DDL, or with short-lived credentials Polaris vends for that table's files. This post is about what happens when there is nothing to vend.

By default, ClickHouse's DataLakeCatalog engine asks Polaris to vend short-lived storage credentials for every table it reads. Our Iceberg catalog sits on OCI Object Storage — S3-compatible, but with no STS behind it — so Polaris has nothing to vend. I got there in three errors, fixed the wrong thing first, and came away thinking one grant was load-bearing. It wasn't.

Three errors, one wrong assumption

  1. ClickHouse logged in as admin → 403 on LOAD_TABLE_WITH_READ_DELEGATION. The admin principal doesn't hold TABLE_READ_DATA, and that is the privilege Polaris checks when a client asks for vended credentials.
  2. Switched to a reader principal that holds TABLE_READ_DATA → 400, Credential vending was requested ... but no credentials are available. Authorization passed; vending failed. On OCI there is nothing to vend.
  3. Set vended_credentials = false → rows. ClickHouse does a plain loadTable and reads Parquet with the static S3 key from the DDL.

I wrote that up as "one privilege makes ClickHouse read your lakehouse." Then I rebuilt it in a lab and found the admin login would have worked at step 3 too. With vending off, Polaris only checks metadata privileges. The grant got me past the first error; the setting is what fixed it — and the setting moved the read guard from Polaris to the bucket key.

Why RBAC looks like this: privileges live on catalog-roles, nowhere else

Polaris authorization is a four-hop chain. You cannot grant a privilege to a principal directly. It attaches to a catalog-role, which a principal-role is bound to, which the principal is a member of.

The admin trap is by design, not a deployment quirk. The catalog_admin role Polaris creates with a catalog carries CATALOG_MANAGE_ACCESS and CATALOG_MANAGE_METADATA; TABLE_FULL_METADATA explicitly leaves out TABLE_READ_DATA and TABLE_WRITE_DATA, and only CATALOG_MANAGE_CONTENT bundles them. So a root credential looks healthy — SHOW TABLES needs only the *_LIST privileges — right up until the first read that asks for delegation.

What ClickHouse asks Polaris for

The one setting that changes the request is vended_credentials. In 26.4.2.10, leaving it unset behaved exactly like true.

The lab

To stop guessing, I rebuilt it locally: Polaris 1.6.0 with Keycloak, MinIO with Polaris vending turned off (close to the position OCI puts you in — the 400 below is the difference), ClickHouse 26.4.2.10, and a three-row demo.events table. Each login, against Polaris directly and through ClickHouse:

Login Polaris loadTable Polaris loadTable + delegation ClickHouse, vending on (default) ClickHouse, vended_credentials = false
reader with TABLE_READ_DATA 200 200 reads rows reads rows
reader without TABLE_READ_DATA 200 403 SHOW TABLES ok, SELECT → UNKNOWN_TABLE reads rows
root, default catalog_admin 200 403 SHOW TABLES ok, SELECT → UNKNOWN_TABLE reads rows

Two things in that table cost me the most time.

First, ClickHouse never shows you the 403. It lists the table in SHOW TABLES, then tells you the same table doesn't exist — for count() as much as for SELECT:

Code: 60. DB::Exception: Unknown table expression identifier 'lk.demo.events' ... (UNKNOWN_TABLE)

The real reason is one log level down. Run the query with --send_logs_level=debug (or SET send_logs_level = 'debug') and Polaris' answer comes back to the client — here is root's, from the same lab:

HTTP status code: 403 'Forbidden' ... Principal 'root' with activated PrincipalRoles '[service_admin]'
and activated grants via '[service_admin, catalog_admin]' is not authorized for op LOAD_TABLE_WITH_READ_DELEGATION

The activated grants via list is the fastest way to see which catalog-roles Polaris actually resolved — and to catch ClickHouse logging in as the principal you didn't mean.

Second, the last column. With vending off, every login read the rows, including the two without TABLE_READ_DATA. On a store that can't vend, that is where you live.

Provision the reader: the curls

Idempotent, and identical locally and on OCI except for the token endpoint and catalog name. Set the management/catalog base URLs and the root bearer token first, then four steps: catalog-role, grants, principal-role, principal.

# 1. Catalog-role that will hold the read grants
curl -s -X POST $MGMT/catalogs/$CATALOG/catalog-roles \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"catalogRole":{"name":"reader_all"}}'

# 2. Grant the read privileges AT CATALOG LEVEL so they cover every namespace.
#    TABLE_READ_DATA matters as soon as anything asks for vended credentials.
for P in TABLE_READ_DATA TABLE_READ_PROPERTIES TABLE_LIST \
         NAMESPACE_LIST NAMESPACE_READ_PROPERTIES \
         VIEW_READ_PROPERTIES VIEW_LIST; do
  curl -s -X PUT $MGMT/catalogs/$CATALOG/catalog-roles/reader_all/grants \
    -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d "{\"grant\":{\"type\":\"catalog\",\"privilege\":\"$P\"}}"
done

# 3. Principal-role, bound to the catalog-role
curl -s -X POST $MGMT/principal-roles \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"principalRole":{"name":"ch_role"}}'
curl -s -X PUT $MGMT/principal-roles/ch_role/catalog-roles/$CATALOG \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"catalogRole":{"name":"reader_all"}}'

# 4. The principal CH logs in as. The RESPONSE carries clientId + clientSecret ONCE.
curl -s -X POST $MGMT/principals \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"principal":{"name":"ch_reader","properties":{}},"credentialRotationRequired":false}'
# -> {"credentials":{"clientId":"...","clientSecret":"..."}}  save it; not retrievable later
curl -s -X PUT $MGMT/principals/ch_reader/principal-roles \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"principalRole":{"name":"ch_role"}}'

The only environment difference is who issues the token, and each row maps to a DDL setting:

local OCI
Token issuer (oauth_server_uri) Keycloak (/realms/<realm>/protocol/openid-connect/token) Polaris (/api/catalog/v1/oauth/tokens)
auth_scope catalog PRINCIPAL_ROLE:ALL
Warehouse scheme s3:// (MinIO) s3a://

On OCI, Polaris issues its own root token:

TOKEN=$(curl -s -X POST \
  https://<polaris-host>/api/catalog/v1/oauth/tokens \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d "grant_type=client_credentials&client_id=<root clientId>&client_secret=<root clientSecret>&scope=PRINCIPAL_ROLE:ALL" \
  | jq -r .access_token)

The 400 on OCI, and what it costs you

Get the grant right and, on OCI, you hit a different wall:

400 Credential vending was requested for bronze.events_raw,
    but no credentials are available

This is not broken RBAC. The principal has TABLE_READ_DATA — a plain loadTable returns 200. The 400 means ClickHouse asked Polaris to mint temporary scoped storage credentials, and the catalog has none to mint. Two different operations: authorization passed, vending failed. (I saw this on OCI; the MinIO lab with vending off answers the delegated call with 200 and no credentials instead.)

The fix is to stop asking Polaris to vend:

vended_credentials = false

Know what that moves. With vending off, Polaris checks metadata privileges (TABLE_READ_PROPERTIES) for the loadTable; the Parquet read is guarded by the key you put in the DDL. So make that key earn it: read-only, scoped to the warehouse prefix, one per reader. Keep TABLE_READ_DATA on the reader anyway — it is what you need the day the store can vend.

The ClickHouse DDL

Use DataLakeCatalog, not iceberg() with inline keys — the catalog is the point. Positional args 2–3 are the static S3 access/secret keys (Polaris is not vending). catalog_credential is the principal's clientId:clientSecret. oauth_server_uri must point at the right issuer.

SET allow_database_iceberg = 1;   -- allow_experimental_database_iceberg on older builds

-- OCI: Polaris issues the token, s3a:// warehouse, no STS behind the store
CREATE DATABASE lake_bronze ENGINE = DataLakeCatalog(
    'https://<polaris-host>/api/catalog',
    '$S3_ACCESS_KEY', '$S3_SECRET_KEY')        -- read-only, warehouse-scoped key
SETTINGS catalog_type = 'rest',
    catalog_credential = '<ch_reader clientId>:<ch_reader clientSecret>',
    warehouse          = '<catalog-name>',
    auth_scope         = 'PRINCIPAL_ROLE:ALL',
    oauth_server_uri   = 'https://<polaris-host>/api/catalog/v1/oauth/tokens',
    storage_endpoint   = '$S3_ENDPOINT',
    vended_credentials = false;   -- no STS behind this store: plain loadTable + static key

For local, point oauth_server_uri at Keycloak, use the s3:// MinIO endpoint, and auth_scope = 'catalog'.

Verify with two curls before touching ClickHouse

Do not debug authorization through ClickHouse — it will tell you UNKNOWN_TABLE. Authenticate as the reader and make both calls ClickHouse can make:

# Token AS ch_reader (its own clientId:clientSecret)
RTOK=$(curl -s -X POST $CAT/oauth/tokens \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d "grant_type=client_credentials&client_id=<ch_reader id>&client_secret=<secret>&scope=PRINCIPAL_ROLE:ALL" \
  | jq -r .access_token)
# empty token -> reach problem, not a grant problem

T="$CAT/$CATALOG/namespaces/bronze/tables/events_raw"
# plain loadTable: what ClickHouse does with vended_credentials = false
curl -s -o /dev/null -w 'plain:     %{http_code}\n' "$T" -H "Authorization: Bearer $RTOK"
# delegated loadTable: what ClickHouse does by default
curl -s -o /dev/null -w 'delegated: %{http_code}\n' "$T" -H "Authorization: Bearer $RTOK" \
  -H 'X-Iceberg-Access-Delegation: vended-credentials'
# delegated 403 -> ClickHouse shows UNKNOWN_TABLE; the principal lacks TABLE_READ_DATA
# delegated 400 -> nothing to vend; set vended_credentials = false

The decoder

Symptom Cause Fix
SHOW TABLES lists it, SELECT / count() → UNKNOWN_TABLE Hidden 403: delegated loadTable denied, principal lacks TABLE_READ_DATA Check with --send_logs_level=debug or the curl; log in as the reader, or grant TABLE_READ_DATA
SELECT → UNKNOWN_TABLE, delegated curl is 200 Table has no committed snapshot yet (seen once on OCI) Not RBAC — wait for the writer to flush
400 Credential vending ... no credentials are available RBAC fine, but the store can't vend (OCI) vended_credentials = false and a read-only, scoped key
Code 48 Unsupported storage type: s3a The 25.3 build I had refused s3a:// Use CH 26.x (or re-register the catalog s3a → s3)
Code 117 MEMORY_LIMIT_EXCEEDED ("Cannot read Iceberg avro manifest") A small-files table's manifest is too big for the node (I hit it at ~16k files) Not RBAC — bigger node, or compact the table (fewer files → smaller manifest)
Token endpoint 501 / "unexpected end of data" CH pointed at the wrong OAuth issuer Point oauth_server_uri at Keycloak (local) / Polaris (OCI)

What not to over-cook

One catalog-role with the read-only set. One principal-role. One principal. One read-only key. That is the whole configuration. Do not grant read-write or admin to the reader, do not vend per-table credentials, and do not reach for icebergS3() to route around the catalog. The discipline is the design.

Once reads work, prune tight: filter on the table's event-time column, because a full scan over many small files is slow and a tight predicate is not. And past a certain file count this stops being a tuning problem and becomes a compaction one — once a table has enough small files, even reading its manifest can OOM before any predicate runs.

The table and the log lines come from the lab (Polaris 1.6.0, ClickHouse 26.4.2.10, MinIO); the three errors, the 400 and the manifest OOM come from OCI. The one table that still wouldn't read there was that OOM — compaction, not RBAC.
