Why adding a column is a planned stop: schema evolution on a positional Flink → ClickHouse sink

4 November 2026

When a Flink job writes to ClickHouse as positional RowBinary, adding a column to the table is not an ALTER and a redeploy; it is a planned stop. The writer and the table have to agree on the byte layout at every moment, and a stateful job carries old-layout rows across the restart inside its savepoint.

Get it wrong and the job looks fine: it shows RUNNING between crashes, dashboards look alive, and nothing lands. In the worst case ClickHouse accepts the mis-shaped bytes and stores garbage. This is the procedure we ended up with, and why each step is there.

The setup: a stateful Flink job (RocksDB, savepoints, run by the Flink Kubernetes Operator) writing through our own async sink. The NATIVE savepoint format and the formatType field need Flink 1.15 or later.

The core constraint

The Flink job writes to ClickHouse using positional RowBinary: rows are serialised as raw bytes in table-column order with no column names attached. ClickHouse decodes them by assuming the byte layout matches its current column list exactly.

This makes writes fast, but it means the writer and the table must agree on the layout at all times. If the table has 12 columns and the job sends 10-column rows, ClickHouse cannot find row boundaries and usually rejects the whole batch with Code: 33 CANNOT_READ_ALL_DATA (or Code: 32 for a single short row).

Usually. In a lab on ClickHouse 26.4.2.10 I sent old-shape rows into a widened table, and when the byte count happened to divide into whole new-shape rows — easy with fixed-width columns — the batch was accepted and stored as garbage. A type change is a layout change too: after MODIFY COLUMN a Nullable(String), an old writer's 1,000 rows were accepted without a single error, with wrong ids and half the values NULL, because Nullable adds a null-flag byte per value. An error is the good outcome here.

Consequences:

  • You cannot widen the table while the old writer is running — its next batch fails, or worse.
  • You cannot start the new writer before the table is widened — its first batch fails (or lands as garbage, same rule).
  • Schema evolution is therefore a planned stop, not a rolling change.

The cheap way out, if you can take it: name the columns. INSERT INTO t (c1, …, cN) FORMAT RowBinary removes the count coupling (RowBinaryWithNamesAndTypes should do the same by name; I only tested the column list) — in the lab an old 4-column writer inserted cleanly into a widened 6-column table, and the new columns took their defaults. Our sink still sends bare positional rows; until it names its columns, the rest of this post is the price we pay.

Three surfaces, not one problem

What gets called "schema evolution" is three independent layers. A fix for one does nothing for the others. This post is mostly about L3; L2 is the tool it borrows, and L1 gets a short section near the end.

Layer Surface Constraint Failure if ignored How it evolves
L1 Flink keyed state (RocksDB) Serializer must match on restore Serializer mismatch → job never starts POJO state evolves natively; Kryo state cannot (see below)
L2 Operator identity (UID) Savepoint state is keyed by operator UID Renamed operator → restore fails without allowNonRestoredState; with it, the state is dropped with only a log line Deliberate rename + one-shot allowNonRestoredState
L3 ClickHouse sink + table Positional writer; async sink buffers rows Old-shape rows meet new-shape table → Code 33, or rows stored as garbage Drained stop → ALTER → restart (this post)

L3 — the sink buffer problem

The sink does not write one row at a time. It packs each row into bytes at the moment it enters the buffer, in the table's current shape, and sends one large batch per HTTP request every few seconds.

A normal stop saves the buffer. stop with drain: false (the default) finishes in-flight requests but does not empty the buffer. Whatever is still waiting is serialised into the savepoint in the old shape.

Then the table is widened.

The new job restores and replays the buffer. Old-shape rows hit the new-shape table → Code 33. Our sink treats that error as non-retryable, so the task crashes, restarts, restores the same buffer, and crashes again. The job shows RUNNING between crashes; dashboards look alive; nothing lands.

The mechanism that makes it safe

1. Drained stop

POST /jobs/{jid}/stop with {"drain": true, "formatType": "NATIVE"}.

With drain, Flink signals end-of-input to every operator, the sink flushes everything it holds (SinkWriterOperator.endInput() → flush(true) runs only under StopMode.DRAIN), and only then takes the savepoint. The savepoint carries an empty buffer.

Proof the drain happened: the JobManager log shows Terminate Savepoint … formatType=NATIVE, not Suspend Savepoint. The final job state FINISHED only proves the stop completed — a stop without drain ends in FINISHED too.

Drain sends a final MAX watermark, which fires every pending event-time timer and window. Flink's own advice is not to drain a pipeline you intend to resume later. We drain anyway because our job uses only processing-time timers, and a drain does not fire those; an event-time job has to make that call deliberately.

2. NATIVE savepoint format

The REST /stop body defaults to CANONICAL; pass formatType yourself. CANONICAL re-serialises all state through the TaskManager; on tens of GB of RocksDB state this caused a TaskManager to drop out mid-savepoint for us. NATIVE copies RocksDB's own files as-is. It needs the same state backend on restore; rescaling still works. We keep parallelism anyway.

3. Widen the table — shard first, then Distributed

ALTER TABLE db.shard_tbl ADD COLUMN IF NOT EXISTS c1 T1 AFTER last_col, ADD COLUMN IF NOT EXISTS c2 T2 AFTER c1;
ALTER TABLE db.dist_tbl  ADD COLUMN IF NOT EXISTS c1 T1 AFTER last_col, ADD COLUMN IF NOT EXISTS c2 T2 AFTER c1;
  • Replicated database engine → the bare statement fans out via Keeper. ON CLUSTER <your remote_servers cluster> fails ("ON CLUSTER is not allowed for Replicated database"); ON CLUSTER <the database's own name> is dropped silently; newer versions have ignore_on_cluster_for_replicated_database to make it a no-op (from the ClickHouse source; my lab has no Keeper, so not reproduced).
  • Non-Replicated → add ON CLUSTER, or only one node is widened.
  • The writer's N must equal the columns an INSERT without a column list fills: ordinary and DEFAULT columns count; MATERIALIZED and ALIAS don't, and positional inserts skip them (checked in the lab). EPHEMERAL columns are skipped too, per the ClickHouse docs. So a column the writer will send must be an ordinary stored column.
  • Column order matters because the writer is positional. Append at the tail.

Then verify every node has the new count before deploying anything:

SELECT hostName(), table, count(1)
FROM clusterAllReplicas('cluster', system.columns)
WHERE database = 'db' AND table IN ('dist_tbl', 'shard_tbl')
  AND default_kind NOT IN ('MATERIALIZED', 'ALIAS', 'EPHEMERAL')
GROUP BY 1, 2;

One node short → that node alone enters the Code 33 loop.

4. Restart with a renamed sink UID

The buffered rows live in the savepoint under the sink's operator UID. Renaming the sink (…-sink-v1 → …-sink-v2) means the restore cannot map the old buffer to any operator, and with allowNonRestoredState: true it is discarded.

This is the backstop for cases where the restore does not actually come from the drained savepoint — e.g. the operator falls back to a retained checkpoint, or the drain silently failed. The sink has no buffer-depth gauge, so emptiness cannot be observed directly; the rename guarantees it.

Rename and flag are one decision: rename ⇒ flag required; no rename ⇒ no flag. Never mix.

job:
  upgradeMode: savepoint          # never stateless
  allowNonRestoredState: true     # one-shot
  initialSavepointPath: s3://…/savepoint-xxxxxx-hash
  savepointRedeployNonce: 2       # must change on every redeploy from a savepoint
podEnv:
  - name: CLICKHOUSE_SINK_UID
    value: "…-sink-v2"

On an existing deployment the path only takes effect with a new savepointRedeployNonce; a first deployment reads it as is.

5. Verify what was discarded

allowNonRestoredState discards anything it cannot map, and the only trace is a log line. After restart, grep the JobManager log for Skipping savepoint state for operator. Expect exactly as many lines as UIDs you renamed on purpose — for a sink-only change, exactly one, and its operator id is the hash of the old sink UID. Any extra line is state you did not mean to lose.

Then confirm the correlator restored: /jobs/{jid}/checkpoints shows latest.restored.is_savepoint = true, and the first checkpoint after the restore shows non-trivial per-operator state sizes.

6. Remove the one-shots

Second config commit: allowNonRestoredState: false, remove initialSavepointPath. The path is the operator's documented redeploy-from-savepoint mechanism; leaving a stale one there means the next nonce bump rewinds to it. And the flag, left on, hides the next real state mismatch.

Full sequence

Preconditions green (uptime, no recent sink failures, ClickHouse memory headroom, no heavy merges)
  → POST /stop {drain:true, formatType:NATIVE}
  → poll /jobs/{jid}/savepoints/{request-id} until COMPLETED with a non-empty location and no failure-cause
  → JobManager log shows Terminate Savepoint
  → ALTER shard, then Distributed
  → assert N_NEW insertable columns on every node
  → deploy new image + new sink UID + one-shot flag + savepoint path
  → JM log: skipped operators == only the UIDs you renamed
  → watch numRestarts, Code 33 count, new columns populating
  → clear one-shots

L1 — keyed state evolution

Flink keyed state evolves only if its serializer supports it. POJO-serialised state evolves in place (fields added/removed with defaults). Kryo GENERIC state cannot evolve; adding a field to a Kryo-reachable graph produces a KryoException on restore and an infinite RESTARTING loop.

Approach taken for the Kryo-frozen correlator:

  • New POJO state class under a new operator UID (…-correlator-v2).
  • New fields carried outside the Kryo graph, in an envelope filled at parse time and projected before any hop that copies the record. A Java transient field does not do this job: both Kryo's FieldSerializer and Flink's PojoSerializer.copy() drop it.
  • Old Kryo state under the old UID is deliberately not restored on cutover — an accepted trade-off against a permanent dual-read hybrid.

That cutover used the same L2 mechanism as the sink (UID rename + one-shot flag), so its skipped-operator count was two, both intended.

What needs no manual step

  • Iceberg sink — evolves its table schema automatically.
  • Duplicates after restart — the sink is at-least-once; ReplacingMergeTree collapses replays on merge.

Signals to trust and not trust

Trust Do not trust
JM log Terminate Savepoint / Skipping savepoint state Job state FINISHED as proof of a drain (a plain stop ends there too)
numRestarts, exception history, system.query_log exception_code 33 COMPLETED savepoint status alone (can carry an empty location + failure-cause)
The first checkpoint's per-operator state sizes after restore Our sink's error, dropped-record and retry counters — they read 0 across real failures: the task dies instead of counting, and the counters reset per attempt
"isStoppable": false in the job overview — it does not block /stop

Rollback

Failure point Action
Savepoint never COMPLETED / no Terminate Savepoint Table untouched. Do not cancel: unless checkpoints are retained on cancellation, cancel drops your restore point. Restart the old image unchanged.
ALTER done, deploy failed Prefer roll-forward. Otherwise drop the new columns (Distributed first, then shard) and redeploy the old image + old sink UID from the same savepoint.
Deployed but wrong (extra skipped operators, near-zero state, Code 33) Old image from the same savepoint, sink UID bumped again (never reuse a UID whose saved state may be a different width).

The Code 32/33 behaviour, the silent-accept cases and the explicit-column-list escape are from a lab on ClickHouse 26.4.2.10. The Flink behaviour is from the Flink docs plus what our job did in production.
