One Privilege Makes ClickHouse Read Your Iceberg Lakehouse

25 June 2026

Polaris RBAC, credential vending, and the DataLakeCatalog engine: what actually decides whether SELECT returns rows.

ClickHouse reads an Iceberg bronze layer through the DataLakeCatalog engine the moment the principal it authenticates as holds one privilege: TABLE_READ_DATA. Without it, every full-scan read returns a 403 on LOAD_TABLE_WITH_READ_DELEGATION. Everything else (the OAuth issuer, the S3 keys, the catalog name) is plumbing you only debug once that grant is in place.

This is the minimal recipe: why the RBAC chain looks the way it does, why credential vending bites you right after RBAC stops biting you, and how to drive ClickHouse so a half-configured catalog never burns your afternoon. Verified locally (ClickHouse 26.4, MinIO s3://) and on preprod (S3-compatible object store, s3a://).

The one thing

TABLE_READ_DATA, granted to a read-only catalog-role, attached to a principal-role, bound to the principal ClickHouse logs in as. That single grant is load-bearing. The trap is that admin and catalog_admin roles do not include it, so federating ClickHouse as a root credential looks healthy right up until the first real column read.

Why RBAC: privileges live on catalog-roles, nowhere else

Polaris authorization is a four-hop chain. You cannot grant a privilege to a principal directly. It attaches to a catalog-role, which a principal-role is bound to, which the principal is a member of.

Here is the part that costs people a day. SHOW TABLES and count() succeed with only TABLE_LIST: those are manifest-level operations and never touch a data file. So a principal with admin rights (which carry listing but not TABLE_READ_DATA) passes every smoke test you would casually run, then 403s the instant you SELECT an actual column. The fix is never "give the reader more power." It is "stop authenticating as root; authenticate as a principal whose catalog-role holds TABLE_READ_DATA."

What ClickHouse actually does at runtime

Two things can go wrong, and they fail at different hops. Knowing which hop you are on tells you whether you have a reachability problem or a grant problem.

Fails at the token endpoint with External access is not allowed: the principal is reachable internally only. This is a reach problem, not a grant problem. Retry; if it persists, make the principal externally reachable or run ClickHouse inside the perimeter.

Fails at loadTable with 403 ... LOAD_TABLE_WITH_READ_DELEGATION: the calling principal lacks TABLE_READ_DATA, almost always because ClickHouse fell back to the admin/root principal.

Provision the reader: the curls

Idempotent, and identical locally and on preprod except for the token endpoint and catalog name. Set the management/catalog base URLs and the root bearer token first, then four steps: catalog-role, grants, principal-role, principal.

# 1. Catalog-role that will hold the read grants
curl -s -X POST $MGMT/catalogs/$CATALOG/catalog-roles \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"catalogRole":{"name":"reader_all"}}'

# 2. Grant the read privileges AT CATALOG LEVEL so they cover every namespace.
#    TABLE_READ_DATA is the load-bearing one; the rest just let SHOW/DESCRIBE work.
for P in TABLE_READ_DATA TABLE_READ_PROPERTIES TABLE_LIST \
         NAMESPACE_LIST NAMESPACE_READ_PROPERTIES \
         VIEW_READ_PROPERTIES VIEW_LIST; do
  curl -s -X PUT $MGMT/catalogs/$CATALOG/catalog-roles/reader_all/grants \
    -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d "{\"grant\":{\"type\":\"catalog\",\"privilege\":\"$P\"}}"
done

# 3. Principal-role, bound to the catalog-role
curl -s -X POST $MGMT/principal-roles \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"principalRole":{"name":"ch_role"}}'
curl -s -X PUT $MGMT/principal-roles/ch_role/catalog-roles/$CATALOG \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"catalogRole":{"name":"reader_all"}}'

# 4. The principal ClickHouse logs in as. The RESPONSE carries clientId + clientSecret ONCE.
curl -s -X POST $MGMT/principals \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"principal":{"name":"ch_reader","properties":{}},"credentialRotationRequired":false}'
# -> {"credentials":{"clientId":"...","clientSecret":"..."}}  save it; not retrievable later
curl -s -X PUT $MGMT/principals/ch_reader/principal-roles \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -d '{"principalRole":{"name":"ch_role"}}'

The only environment difference is who issues the token:

local preprod
Token endpoint Keycloak (/realms/iceberg/.../token) Polaris internal (/api/catalog/v1/oauth/tokens)
Root client polaris-admin, scope=catalog admin, scope=PRINCIPAL_ROLE:ALL
Catalog base s3:// (MinIO) s3a:// (S3-compatible)
ClickHouse version any (s3://) 26.x (s3a:// on 25.3 is NOT_IMPLEMENTED)

On preprod there is no Keycloak; Polaris issues its own root token:

TOKEN=$(curl -s -X POST \
  https://<polaris-host>/api/catalog/v1/oauth/tokens \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d "grant_type=client_credentials&client_id=admin&client_secret=$POLARIS_ROOT_SECRET&scope=PRINCIPAL_ROLE:ALL" \
  | jq -r .access_token)

Why vending bites you next: the 400

Get the grant right and you can still hit a different wall:

400 Credential vending was requested for bronze.events_raw,
    but no credentials are available

This is not broken RBAC. The principal has TABLE_READ_DATA; a plain loadTable returns 200. The 400 means ClickHouse asked Polaris to mint temporary scoped storage credentials, and the catalog has none to mint. Two different operations: authorization passed, vending failed.

The fix is to stop asking Polaris to vend:

vended_credentials = false

With that set, ClickHouse does a plain loadTable (which ch_reader is authorized for) and reads Parquet using the static positional S3 keys you passed in the DDL. No Polaris change, no iceberg() table function.

The ClickHouse DDL

DataLakeCatalog bound to Polaris; never the iceberg() table function with inline keys for the catalog path. Positional args 2–3 are the static S3 access/secret keys (Polaris is not vending). catalog_credential is the principal's clientId:clientSecret. oauth_server_uri must point at the right issuer.

SET allow_database_iceberg = 1;

-- PREPROD: Polaris internal issuer, s3a:// base
CREATE DATABASE lake_bronze ENGINE = DataLakeCatalog(
    'https://<polaris-host>/api/catalog',
    '$S3_ACCESS_KEY', '$S3_SECRET_KEY')
SETTINGS catalog_type = 'rest',
    catalog_credential = '<ch_reader clientId>:<ch_reader clientSecret>',
    warehouse          = '<catalog-name>',
    auth_scope         = 'PRINCIPAL_ROLE:ALL',
    oauth_server_uri   = 'https://<polaris-host>/api/catalog/v1/oauth/tokens',
    storage_endpoint   = '$S3_ENDPOINT',
    vended_credentials = false;   -- catalog can't vend; plain loadTable + static keys

Locally, point oauth_server_uri at Keycloak, use the s3:// MinIO endpoint and auth_scope = 'catalog'; any ClickHouse version reads s3://.

Verify RBAC in one curl before touching ClickHouse

Do not debug authorization through ClickHouse. Authenticate as the reader and do the exact operation ClickHouse does. A 200 means ClickHouse will read; a 403 names the missing grant.

# Token AS ch_reader (its own clientId:clientSecret)
RTOK=$(curl -s -X POST $CAT/oauth/tokens \
  -H 'Content-Type: application/x-www-form-urlencoded' \
  -d "grant_type=client_credentials&client_id=<ch_reader id>&client_secret=<secret>&scope=PRINCIPAL_ROLE:ALL" \
  | jq -r .access_token)
# empty / "External access is not allowed" -> reach problem, not a grant problem

# The decisive check: loadTable WITH read delegation
curl -s -o /dev/null -w '%{http_code}\n' \
  "$CAT/$CATALOG/namespaces/bronze/tables/events_raw" \
  -H "Authorization: Bearer $RTOK" \
  -H 'X-Iceberg-Access-Delegation: vended-credentials'
# 200 -> RBAC OK, ClickHouse will read
# 403 "not authorized for op LOAD_TABLE_WITH_READ_DELEGATION" -> reader_all lacks TABLE_READ_DATA

If the plain loadTable returns 200 but the delegation call returns 400, that is the vending case above: set vended_credentials=false and move on.

The 403/400 decoder

Symptom Cause Fix
403 ... LOAD_TABLE_WITH_READ_DELEGATION Calling principal lacks TABLE_READ_DATA, usually because ClickHouse used admin/root Federate as ch_reader, or grant TABLE_READ_DATA to its catalog-role
400 Credential vending ... no credentials are available RBAC fine, but the catalog has no vendable storage credentials vended_credentials=false: plain loadTable + static keys
External access is not allowed Principal reachable internally only Retry; make the principal externally reachable or run ClickHouse in-perimeter
Code 48 Unsupported storage type: s3a ClickHouse 25.3 + s3a:// warehouse Use ClickHouse 26.x (or re-register the catalog s3a → s3)
Code 117 MEMORY_LIMIT_EXCEEDED ("Cannot read Iceberg avro manifest") A small-files table's manifest is too large for the node (e.g. ~16k files on a ~2 GiB node) Not RBAC: a bigger node, or compact the table (fewer files, smaller manifest)
SHOW TABLES ok, SELECT → UNKNOWN_TABLE Table has no committed snapshot yet Not RBAC: wait for the writer to flush
Token endpoint 501 / "unexpected end of data" ClickHouse pointed at the wrong OAuth issuer Point oauth_server_uri at Keycloak (local) / Polaris (preprod)

What not to over-cook

One catalog-role with the read-only set. One principal-role. One principal. That is the whole configuration. Do not grant read-write or admin to the reader, do not vend per-table credentials, and do not reach for icebergS3() to route around the catalog. The discipline is the design.

One operational note once reads work: when ClickHouse reads the lake remotely, scans run against many small files, so prune tight. Prune each table on its event-time column; for tables whose fields sit in a nested struct (say data.event.*), that is often a top-level timestamp. A full-table scan is slow; a tight predicate on the right column is not. And past a certain file count this stops being a tuning problem and becomes a compaction one: once a table has enough small files, even reading its manifest can run out of memory before any predicate runs.

Verified

  • Local (ClickHouse 26.4, MinIO s3://): ch_reader / reader_all / TABLE_READ_DATA read bronze and joined silver at 100%.
  • Preprod (s3a://, vended_credentials=false): the engine reads events_raw, sessions_bucketed and orders_bucketed. The earlier 403 was only ClickHouse authenticating as admin/root; as ch_reader, authorization passes and a plain loadTable is 200.
  • The one table that still fails is not an RBAC failure. logs_bucketed authenticates fine and reaches the manifest, but the query runs out of memory reading a ~16k-file Iceberg avro manifest on a ~2 GiB node (Code 117 MEMORY_LIMIT_EXCEEDED). That is the small-files problem at the manifest level, and iceberg() hits the same wall because it reads the same manifest. Fix it with a larger node or by compacting the table; do not touch RBAC.
