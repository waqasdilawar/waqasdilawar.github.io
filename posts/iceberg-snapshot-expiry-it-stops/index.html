Iceberg doesn't slow down when you skip snapshot expiry. It stops.

4 November 2026

A production Flink job that restarted every few hours, a stack trace that said "out of memory" and meant "you forgot to take out the trash," and a maintenance job that made things worse before it made them better.

Our Flink streaming job commits to Iceberg tables behind a Polaris REST catalog, on S3 compatible object storage. Every commit adds a snapshot to the table's metadata, and nothing removes it until you run snapshot expiry.

I want to write this one down because the failure looked like one thing and was another, and because I have now watched the same mechanism bite from two directions in the same week. Iceberg is a table format that gives you atomic commits, time travel, and engine independence. What it does not give you is garbage collection. You own that. Skip it long enough and the bill does not arrive as slowness. It arrives as a writer that cannot commit at all.

The restarts

Our production correlation job — Flink 2.2, RocksDB, writing to both ClickHouse and an Iceberg silver layer behind a Polaris REST catalog — had restarted sixteen times in forty-four hours. Forty-eight failed checkpoints out of about 2,600. Nobody had been paged. The job self-heals: it dies, restarts from the last checkpoint, replays, catches up. From the outside it looked like a slightly bumpy pipeline. Reporting freshness took a hit every few hours and then recovered. Nothing was lost.

That is exactly why it ran for two days before anyone looked closely.

When I finally pulled the exception history, ten of the fifteen recorded failures (the history is capped) were the same stack trace, byte for byte:

java.lang.OutOfMemoryError: Java heap space
  at org.apache.hc.core5.util.CharArrayBuffer.expand
  at org.apache.hc.core5.http.io.entity.EntityUtils.toString
  at org.apache.iceberg.rest.HTTPClient.extractResponseBodyAsString
  at org.apache.iceberg.rest.RESTTableOperations.refresh
  at org.apache.iceberg.SnapshotProducer.refresh
  at org.apache.iceberg.SnapshotProducer.commit
  at org.apache.iceberg.flink.sink.dynamic.DynamicCommitter.commit

It hit the main sink committer and the dead-letter sink committer. It hit four different TaskManagers. So it was not a bad node and it was not one table. It followed the workload.

What the trace is actually saying

Read it bottom-up. The Flink committer is committing a snapshot. To do that, Iceberg first refreshes its view of the table — it asks the catalog for the current table metadata. Over REST, that means an HTTP GET whose body is the entire metadata JSON document, read into memory as a single string.

That document is the table. It holds the schema, the partition spec, the properties, and — this is the part that matters — the full list of every snapshot the table has taken since the last time somebody expired them. A streaming job that checkpoints every minute adds well over a thousand snapshots a day. None of them go away on their own.

The thing that bounds this document is snapshot expiry, not compaction. Compaction alone makes it worse, because every rewrite is one more snapshot. (Newer clients can ask for snapshots=refs and get a smaller response. That trims what you fetch, not what the table holds.)

Our snapshot expiry was about twenty-four days behind. The silver tables had never been compacted or expired at all. So the metadata document had been growing linearly for weeks, and the committer's heap — sized sensibly for the work a committer does — eventually could not hold a string that large. CharArrayBuffer.expand asked for more, there was no more, the task died.

Then Flink restarted the job, it caught up, it committed again — and the metadata was now one snapshot bigger. Which is why the restarts were getting closer together.

What the growth looks like

To put a shape on it, I reproduced the growth in a small lab (November 2026): Polaris 1.6.0 with MinIO, PyIceberg 0.12, a two-column table, one single-row append per commit, and the size of the loadTable response body after each batch of commits:

commits loadTable response snapshots in the metadata
1 1.7 KB 1
100 75 KB 100
250 165 KB 250
500 314 KB 500
after expiring all but the current snapshot 17 KB 1

About 620 bytes per commit, linear, for a table with almost nothing in it. (After expiry the document is still ten times its day-one size: what remains is the log of previous metadata files, which Iceberg caps at 100 entries by default, so that part stops growing on its own.) At one commit a minute that is at least 0.9 MB a day per table — on paper, about 21 MB after twenty-four days — and the committer reads all of it on every commit. Commits also got slower as it grew, from about 0.08 s each at 50 commits to 0.2 s at 500 — a slowdown nobody notices at one commit a minute, which is the point. The lab shows the growth and the shrink; it doesn't reproduce the OOM, and I didn't measure the production document.

The trap I nearly walked into

The stack trace says out of memory. The obvious lever is more memory. Bump the TaskManager heap, or at least the committer slot, and the restarts stop.

They would stop — for a few weeks. The document keeps growing. You have bought time and fixed nothing, and the next time it fails the heap is bigger and so is the blast radius.

There is a second, subtler trap here too, and I want to name it because we had another memory problem on a sibling job the same month. That one was a cgroup kill: exit code 137, OOMKilled in the pod status, visible only in the JobManager log. The fix for that class is container limits, MALLOC_ARENA_MAX, off-heap tuning. This one is an in-JVM heap OOM with a named allocation site. Same word, different disease, different medicine. If you reach for the pod-limit lever on a heap OOM you will be confused for a long time.

The real fix is boring: run snapshot expiry, bring retention down to something deliberate, and keep it running on a schedule so the document stays bounded. Which is what we set out to do.

The maintenance job that made it worse first

We already had an Iceberg maintenance job for the bronze tables — a Flink job using the built-in table maintenance operators to bin-pack small files and expire snapshots. Six tables, healthy, had been running for weeks. So the plan was straightforward: stand up a second instance pointed at the silver namespace.

The first thing that happened was that it did nothing at all, while reporting RUNNING.

All 224 tasks sat in scheduled. Zero TaskManagers registered. The exceptions endpoint was empty. From every dashboard we had, the job was healthy and idle. The only place the truth appeared was the JobManager log: 41 TaskManager pods created, 40 terminated with exit code 1 about six seconds after birth, before they could register. The values file had been copied from the bronze job and had lost the volume mount for a local working directory while keeping the config that pointed at it. The container runs as a non-root user; it could not create the directory at the image root; it exited. Ten-minute fix once found. But I want to underline that a maintenance job can be completely dead and look fine, and if your alerting is on job state rather than tasks-actually-running you will not know.

The second thing that happened was the interesting one. With the volume fixed, the job deployed — and within thirty minutes Polaris was in CrashLoopBackOff.

The silver namespace resolved to fourteen tables. The maintenance job builds a small pipeline per table, so that came to roughly 154 operators across 224 tasks. Every one of those operators, on open, calls loadTable against the catalog. And every one of those fourteen tables had never been maintained, so every one of their metadata documents was the same kind of bloated thing that had just been killing my committer.

Polaris was a single replica with a 6 GiB memory cap. Its working set sawtoothed from 1.6 GiB up to 5.97 GiB, and it got killed two different ways. First by the liveness probe — the GC pauses under that much allocation stalled the health endpoint past the probe's patience, and Kubernetes sent SIGTERM then SIGKILL, which showed up in the pod status as exit 137 with reason Error. Then, a little later, by a genuine cgroup OOM. I initially called all of it "OOMKilled" and had to correct myself, because the two need different fixes: the probe needs to be more patient, and the pod needs more room.

Meanwhile the maintenance job retried every ninety seconds, and every retry fired another 154 loadTable calls at a catalog that was still getting back on its feet. A tidy feedback loop. The bronze maintenance job, pointed at its six well-kept tables, ran through the whole thing without a blip.

The moment we stopped the silver job, Polaris stopped crashing on its own. Which was the confirmation I needed: the maintenance job intended to shrink the metadata had knocked over the catalog by reading the metadata it was about to shrink. The first pass over a never-maintained table is by far the most expensive one. Steady-state maintenance on a well-kept table is cheap. The debt compounds, and the interest is paid on the first repayment.

The scare that turned out fine

There is a sub-plot I had been carrying for weeks. Our object storage is an S3 compatible endpoint, not AWS S3. I had a long-standing suspicion — from an earlier incident — that it was rejecting the bulk delete requests Iceberg issues during snapshot expiry, over a checksum header the AWS SDK adds. If that were true, expiry would have been removing references from the metadata while leaving every file on disk. A smaller metadata document, the same storage bill, and orphan files forever.

I had written "fix the delete path" into the plan as a hard precondition. Before acting on it I checked. I pulled about nine hours of the bronze maintenance job's TaskManager log — 684,000 lines — and grepped for every failure signature I knew: Failed to delete object, Deleted only 0 of N files, InvalidRequestException. Zero, zero, zero. Then I reconciled what expiry had scheduled against what the two delete subtasks reported: 265 scheduled, 133 + 132 deleted. 113 scheduled, 57 + 56. Every table, exactly.

The two JVM flags we had set some time ago — -Daws.requestChecksumCalculation=when_required and -Daws.s3.disableChunkedEncoding=true — were the fix, not the bug; at least nothing in nine hours of logs says otherwise. I had been carrying a belief that was no longer true and nearly spent a day on it.

One honest caveat: proving that the delete calls succeed is not the same as proving that the storage footprint dropped. That is a separate measurement and it is still on my list.

Where it stands

Polaris first: memory cap from 6 to 12 GiB. There is no explicit -Xmx in the deployment, and the base image sizes the heap as a percentage of the container limit, so this lever actually works. Liveness probe relaxed so a long GC pause is not a death sentence.

Then the silver maintenance job, in batches. Not silver.* — an explicit list of the three smallest tables, then the next few, six batches in all, with the biggest table alone in the last one. Promote a batch only after the previous one has completed a full compaction-and-expiry cycle with the catalog stable.

The catalog is a single replica with autoscaling off, and every Iceberg writer in the platform depends on it. Resizing is the stopgap. Making it not a single point of failure is the fix.

What I am taking away

  • Iceberg metadata grows on every commit and never shrinks on its own. Snapshot expiry is not hygiene. It is part of the write path. Schedule it before the first streaming writer goes live, not after the first outage.
  • Alert on snapshot count and metadata file size per table. Those are the leading indicators. Committer heap usage is the lagging one, and by the time it fires you are already restarting.
  • Do not fix a heap OOM with more heap. Read the allocation site. If it is a metadata read, the metadata is the problem.
  • "OOM" is two diseases. In-JVM heap exhaustion and cgroup OOMKilled have different signatures and different fixes. Check which one you have before you touch anything.
  • The catalog reads the same bloated documents your writers do. Size it for the burst of a full maintenance sweep, not the steady state, and do not run it as a single replica.
  • Never do a first pass on *. Smallest tables first, one batch at a time, biggest table alone at the end.
  • A maintenance job can be dead while reporting healthy. Alert on tasks running and last successful cycle, not on job state.
  • Verify your beliefs about the object store. "Expiry runs" and "storage is reclaimed" are two claims. I had the wrong answer to the second one for weeks. Reconcile scheduled deletes against completed ones, and then go check the bucket.

The pipeline self-healed every single time, and no data was lost. I keep coming back to that, because it is the reason this was easy to ignore for two days — and the reason the metadata kept growing while we ignored it.
