Finding one row fast: sort, bloom, and the compaction you can't skip

4 November 2026

The lookup is one row by a high-cardinality id that isn't the leading sort key anywhere. The data sits in two layers: a ClickHouse silver table, and an Iceberg bronze layer underneath it in Parquet. Each needed a different fix, and I measured both.

The short version

  • Silver (ClickHouse): add one bloom_filter skip index on the id — 49–81× fewer rows read in the lab, two ALTERs, no re-sort.
  • Bronze (Iceberg): turn the Parquet bloom on as a table property and every writer that honors it, the sink included, writes it from the first commit. A lookup then reads about one row group instead of all of them: ~5× fewer rows on a fresh five-row-group file, ~50× on the compacted fifty-row-group table. A Spark sort-rewrite is the follow-up that adds file-level range pruning.
  • Compaction isn't what makes the bloom work. It is what makes the manifest loadable and the file count small enough for the rest to matter.

The problem

Start with the thing that trips people coming from OLTP: there are no secondary indexes here. Analytical engines don't point-chase down a B-tree; they skip data they can prove they don't need. That pruning comes from three places — how the data is laid out (partition and sort), the min/max statistics per file and per row group, and bloom filters. So "make this lookup fast" isn't "add an index" in the OLTP sense. It's "give the engine something to prune with."

My id — call it correlation_id, the thing that stitches one request together across sources — is high-cardinality and isn't the leading sort key anywhere. In the silver table it's the second sort key, so a lookup that doesn't also pin the leading column can only use the primary index through ClickHouse's generic exclusion search, and with a high-cardinality leading column that skips almost nothing. In bronze it's written in arrival order, so its values are scattered across every file and the min/max can't rule anything out. Both scan. For an equality lookup on an unsorted high-cardinality column, the right tool is a bloom filter — it answers "might this group hold the value?" cheaply, and lets the reader skip the ones that can't.

Silver: a skip index

In ClickHouse the fix is a bloom-filter skip index — about ten bits per value at a one-percent false-positive rate, enough to skip granules that can't contain the value:

ALTER TABLE silver.events
  ADD INDEX idx_corr correlation_id TYPE bloom_filter(0.01) GRANULARITY 1;
ALTER TABLE silver.events MATERIALIZE INDEX idx_corr;

No re-sort, no rewrite. On a sharded cluster you run it ON CLUSTER against the shard-local table. Measured on ClickHouse 26.4.2.10 with a 2M-row ReplacingMergeTree laid out like the real one (the id as the second sort key, 1,000 distinct values in the leading column), looking up a single value:

layout rows read vs baseline
id as 2nd sort key, no skip index 2,000,000 baseline (245 of 245 granules)
+ bloom_filter(0.01) skip index 24,576 81× fewer
id as the leading sort key 8,192 244× fewer (1 granule)

My first run gave 31.6× on a differently shaped table; the lab gives 49× to 81× depending on the leading column. One thing the lab turned up: with only a handful of values in the leading column (four, in one run), the exclusion search already prunes on the id — the bare lookup read 7 of 245 granules — so check EXPLAIN indexes = 1 before you bother.

The last row is the trap. Leading with the id is faster still, but the sort key is the table's one primary index and it already serves the main access pattern; in a ReplacingMergeTree it is also the dedup key, so it isn't something to rearrange for a second lookup, and changing it means rebuilding the table. If that second access pattern were truly hot you'd serve it with a re-sorted materialized view or a projection. The skip index is the cheap first move.

Bronze: layers of pruning

Iceberg prunes in layers: partition, then file (via the manifest's min/max), then row group (via the Parquet footer's min/max and the Parquet bloom filter). Sorting on the id narrows the min/max so whole files and row groups drop at planning. A bloom filter on the id lets the reader skip row groups that can't contain it. The bloom is a table property, set through the catalog, and any writer that honors it writes the filter; the sort depends on which job writes the files. ClickHouse is only the reader here.

First, the mechanism, on a 10M-row Parquet file (77 row groups, one lookup), through ClickHouse 26.4.2.10's Parquet reader with min/max and bloom pushdown on — the same pushdown it uses reading Iceberg:

variant row groups pruned rows read
random order, no index 0 / 77 10,000,000
sort by id (min/max) 76 / 77 26,624
bloom on id (random order) 0 / 77 130,818

ParquetPrunedRowGroups counts only min/max pruning in 26.4; the bloom's skips aren't counted, which is why that row shows 0 pruned while rows read drop about 76×. In the sorted row, the page index trims further inside the one surviving row group.

Two independent mechanisms: sort drops whole row groups at planning from the footer min/max (77 → 1); bloom still visits every row group but skips the decode (10M rows → about one row group's worth), and helps even on unsorted data. Turn bloom pushdown off on the same file and it's back to all 10M rows. Once the file is sorted, the bloom adds nothing for this lookup. And the bloom isn't free on disk: about 15% more file here.

Does it survive the real compaction job?

I set the bloom property on the table, paused the stream, and ran the bin-pack rewrite on its own. About 1.5M source events compacted down to a bronze table of half a million rows in fifty row groups. Then one lookup, with Parquet bloom pushdown off versus on:

lookup on the compacted bronze table rows read
bloom pushdown off (full scan) 500,005
bloom pushdown on (1 of 50 row groups) 10,007 — about 50× fewer

The bin-pack rewrite does write the Parquet bloom filters when the property is set, and ClickHouse uses them whether it reads the file directly or through the federated catalog (identical row counts both ways). But bin-pack cannot sort. Every row group still carries a full-range min/max, so there is no range pruning on top; the bloom alone narrows the read to the row group holding the value, give or take an occasional false positive.

Range pruning needs a sort rewrite, and a sorted rewrite is a Spark procedure; the Flink rewrite action is bin-pack only:

CALL <catalog>.system.rewrite_data_files(
  table => 'bronze.events', strategy => 'sort', sort_order => 'correlation_id');

One caution on sizing: a bloom filter only hits its target false positive rate if it was sized for the number of distinct ids it actually holds. Check write.parquet.bloom-filter-fpp.column.<col> and write.parquet.bloom-filter-max-bytes against your row-group cardinality, or the 1% quietly drifts upward.

The bloom isn't a compaction thing — the sink writes it too

This part surprised me. The bloom isn't a property of compaction at all; it's a property of the table. Any Iceberg writer that honors it writes the bloom, including the Kafka Connect sink. I checked by stopping compaction entirely and ingesting a fresh wave: the brand-new sink-written file (about fifty thousand rows, five row groups) answered the same lookup by reading one row group instead of all five.

lookup on a fresh sink-written file (no compaction) rows read
bloom pushdown off 49,999 (full scan)
bloom pushdown on (1 of 5 row groups) 10,007 — about 5× fewer

Why 5× here and ~50× on the compacted table? Row groups in scope. The bloom narrows the read to the row group holding the value, plus the odd false positive, since a bloom filter answers "maybe", never "yes". This lookup had five row groups to choose from; the compacted one had fifty. So the multiplier is the row-group count, not something compaction adds to the bloom. What compaction adds is what the bloom can't: the filter lives inside each Parquet file, so a lookup across thousands of tiny files still has to open every one of them to consult it. Fewer, bigger files mean fewer opens and a smaller manifest, and a rewrite is the one place that can sort. I measured rows read, not file opens, so that last cost is mechanism, not a number.

You set it once, on the auto-created table, so every file carries a bloom from the first commit:

// Apache Iceberg Kafka Connect sink config
"iceberg.tables.auto-create-props.write.parquet.bloom-filter-enabled.column.correlation_id": "true"

On a table that already exists, set it with ALTER TABLE … SET TBLPROPERTIES ('write.parquet.bloom-filter-enabled.column.correlation_id' = 'true'); writers pick it up on their next refresh.

The part you can't skip: compact first

The bloom works without compaction, but the rest doesn't. Before compaction my bronze layer was thousands of tiny files — around sixteen thousand, each barely over a megabyte. Two things break at once. Min/max has nothing to prune with: the id is scattered across every arrival-ordered file, so every file's range covers your value. And the manifest, Iceberg's list of data files, grows with the file count until it is too big to load; on the node size I had, reading it hit the memory limit before any predicate even ran. That error had nothing to do with permissions or the query and everything to do with file count. The fix isn't a better predicate or a tuning flag. It's compaction, which is also what keeps a bloom lookup from opening thousands of files to find one row group.

The whole recipe

where do this gets you
silver bloom_filter skip index on the id 49–81× in the lab (31.6× in my first run)
silver, if the 2nd pattern is hot re-sorted MV / projection on the id primary-index speed, more CPU and disk
bronze, fresh from the sink turn on the Parquet bloom in the sink's auto-create props ~5× on a five-row-group file (measured), no extra job, from commit #1
bronze, after compaction compact, with the bloom on ~50× on fifty row groups (measured), a loadable manifest, fewer files to open
bronze, follow-up Spark sort-rewrite on the id adds min/max range pruning, file skipping

The silver and Parquet measurements were re-run on ClickHouse 26.4.2.10 in November 2026; the compaction and sink numbers are from my own environment and weren't reproduced in the lab.

Where this comes from

A few sources shaped how I think about this:

  • Jack Vanlightly, Beyond Indexes — open table formats have no secondary indexes; skipping is layout plus min/max plus bloom, and bloom is the right tool for high-cardinality unsorted point lookups.
  • Jack Vanlightly, Have your Iceberg cubed, not sorted — the Qbeast OTree, a multidimensional index for when many columns are filtered (vs a one-dimensional sort).
  • Dremio, How Z-Ordering in Apache Iceberg Helps Improve Performance — Z-order interleaves columns for multi-column pruning; for a single column, a linear sort is the simpler choice, applied via a Spark rewrite.
  • Dremio, A Hands-On Look at the Structure of an Apache Iceberg Table — where the file-skipping min/max actually live: the manifests and the Parquet footers.
  • Sam Rose, Bloom Filters — the visual guide to why a bloom answers "maybe" and how bit count and hash count trade off against the false positive rate.
